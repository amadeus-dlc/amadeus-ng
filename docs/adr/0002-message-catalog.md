# ADR 0002: 文言カタログ — 逐語文言とコマンド語彙の一元管理

- **ステータス**: **Accepted**（2026-08-22 オーナーレビューで確定: 本家踏襲が基本。バイナリはディスパッチャ語彙を正式 CLI とし、素の `aidlc-<tool>` 綴りにはマルチコール方式で応える。敵対的レビュー 1 巡反映済み）
- **日付**: 2026-08-22
- **対応**: `00-policy.md` §3 A3・§2（D6 の互換範囲、逸脱第 1 号）。リスク R5（改名の非原子性）・R2（正規表現の意味論差）の手当て
- **関連**: ADR 0001（正準 JSON）、`01-domain-model.md` §7-2（Published Language クレート層 — message-catalog は独立クレートとしてこの層に属する）

## コンテキスト

upstream ではエラーメッセージ・拒否文言・ゲート文言・継続文言が **LLM エージェントの分岐条件**として機能しており、その逐語文字列がツール（41 本）・フック（17 本）・Markdown 資産・テストに散在している。D6 によりこれらは upstream 互換で凍結するが、起動配線の綴りだけは物理的に置換が必要になる（逸脱第 1 号）。置換漏れ 1 か所が静かな挙動破壊になるため（R5）、生成する側と検出する側（ガードのパーサ、Stop フックの継続文照合、注入フィードバック判定）が同一の定義を参照する構造を最初に作る。

前提として押さえるべき upstream の実態が 2 つある。

1. **コマンド綴りは 3 形が実在する**。(1) bun 直接形（`bun <dir>/tools/aidlc-<tool>.ts <sub>`）、(2) 素の `aidlc-<tool> <sub>` 形（`07-hooks.md:260` の Stop フック継続文に実在 — bun なし・.ts なし）、(3) ディスパッチャ形。バイナリ語彙の正準はディスパッチャ `aidlc.ts` の凍結 ROUTES 表（30 経路）であり、`<noun> <verb>` への変換は**機械的でない**（noun-map の動詞改名、top-prefix、custom の引数再構成、SLASH_FLAG_ALIASES 9 件 — `09-cli-tools.md` §2.1-2.4）。機械的な `aidlc <name> <args>` 導出では upstream のバイナリ語彙に存在しない綴りを生んでしまう。
2. **検出側は JS RegExp で書かれている**。R2 のとおり Rust regex とは受理集合が静かに割れうるため、emit 側の文言一致だけでなく検出側の受理/拒否も固定する必要がある。

## 決定

1. **単一クレート**（仮称 `message-catalog`）に、契約となる逐語文言をすべて定数として集約する。各エントリは次を持つ: 安定 ID、本文（upstream 逐語）、パラメタを型で受けるテンプレート関数、upstream 出典（`file:line` @ `3c3146cf`）、消費者リスト（emit 側 / 検出側）、**ゴールデン採取状態フラグ**（`captured` / `spec-quoted-only`）。
2. **カタログの範囲**は次の 3 区分。(a) エンジン・ツールの stdout / stderr 文言（エラー・拒否・診断）、(b) フックの拒否文言と継続文（Stop フックの 5 形など）、(c) Markdown 資産に埋まるコマンド綴り（パッケージング時変換の対象）。**対象外**: 監査イベント名・状態マーカー・チェックボックス文法 — これらは監査イベントスキーマの Published Language クレート（コンテキスト帰属は `01-domain-model.md` の裁定に従う）が語彙＝型として管理する。
3. **コマンド語彙写像表は upstream ディスパッチャの写し**として定義する。機械的な名前導出規則ではなく、ROUTES 表（30 経路）＋ SLASH_FLAG_ALIASES を写し取り、経路種別（passthrough / 改名 / prefix / custom）ごとに対応を持つ。表の入力側には上記 3 形の綴りをすべて列挙し、出力側のバイナリ語彙は upstream §2.4 の「`<executable> <noun> <verb>`（ディスパッチャ経由）」に一致させる。これは **A1（配布モデル）のバイナリがディスパッチャ語彙を提供することへの明示的依存**である。加えて、素の `aidlc-<tool> <args>` 綴り（Stop フック継続文等に実在し LLM が実行しうる）への互換として、バイナリは**マルチコール方式**（argv[0] が `aidlc-orchestrate` 等ならそのツールとして振る舞う。busybox 式のシンボリックリンク）を採る — これも A1 の ADR が引き受ける要求とする（2026-08-22 オーナーレビューで確定）。Markdown 資産のパッケージング時変換と、文言テンプレート内のコマンド参照は、必ずこの表を引く。
4. **検出側 API を同居させる**。文言を照合する述語（前方一致・正規表現）もカタログが提供し、生成テンプレートと検出パターンを同じエントリに束ねる。片方だけを変更する diff がレビューで必ず不自然に見える構造にする。
5. **CI ゲートを 3 本張る**。
   - (a) **旧綴り残骸 grep**: 生成した配布ツリーとカタログ外のコードに、bun 起動形・`.ts` コマンド参照・**素の `aidlc-<tool> ` 形**の残骸がないことを検査する。ゴールデンフィクスチャのディレクトリ（upstream 実出力は正当に旧綴りを含む）は明示的に除外し、除外リスト自体もカタログ近傍で管理する。
   - (b) **emit 側ゴールデン**: カタログ本文と upstream 実文言（エラーパス含む実出力）の一致。未採取（`spec-quoted-only`）エントリの残数を CI で計数・可視化し、フェーズ A の完了条件として契約経路の全数 `captured` を要求する。
   - (c) **検出側ゴールデン**（R2 の受け皿）: 検出述語を持つ各エントリに、upstream 検出器由来の受理/拒否ゴールデン表を付属させ、Rust 側述語がその表を満たすことを検査する。
6. **ユーザー可視文言の直接組み立てを禁止**する。`format!` 等でユーザー可視文言を作ることはレビュー基準と lint（可能な範囲）で拒否し、必ずカタログ関数を経由させる。
7. **変形クラスへの登録**: コマンド綴り変換は、upstream の T5（`{{HARNESS_DIR}}` トークン置換 — 「唯一許可されたテキスト変形」）に次ぐ**許可された変形の第 2 号**として閉集合に登録する。drift guard は変換込みのビルド再実行で純関数性を検査する。逸脱台帳第 1 号と `01-domain-model.md` §3.6 の不変条件文に相互参照を張る。

## 帰結

- **R5 の範囲（逐語文言とコマンド綴り）については**、変更が「カタログ 1 か所＋写像表」に局所化される。ただし将来の amadeus 改名にはカタログ対象外の変更面（ワークスペースレイアウト、`aidlc-state.md`、`AIDLC_*` 環境変数、CLI 語彙、監査イベント名）が残るため、改名再判断時には Published Language クレート側の語彙定数と合わせた**別 ADR** が必要になる。
- upstream 追従（A7）で文言が変わった場合、カタログ エントリの diff がそのままレビュー単位になる。
- 文言の初期収集という地道な作業が発生する。upstream 仕様 13 本の逐語引用を種にし（`spec-quoted-only`）、stage-0 環境での実行採取で `captured` へ引き上げる。

## 決定順序についての注記

`00-policy.md` §3 の基本順序（A8 → A1 → A3）に先行するが、カタログの規範内容は A8 のワークスペース構成と独立に成立する。決定 3 の写像表は A1 への依存を**明示した上での先行**であり、A1 の ADR はこの依存（ディスパッチャ語彙 `<noun> <verb>` の提供）を引き受けなければならない。クレート名・配置は非規範とし、A8 確定時に追認する。

## 検討した代替案

- **gettext / fluent 等の i18n 基盤**: 不採用。目的は翻訳ではなく逐語固定であり、間接層はバイト一致の検証を難しくするだけ。
- **イベントスキーマクレートへの同居**: 不採用。イベント語彙は型（Published Language）、文言はテンプレートで、変更理由が異なる。ただし両者とも `01-domain-model.md` §7-2 の Published Language クレート層に属する点は同じ。
- **文言をコード近傍に分散させ grep で守る**: 不採用。検出側との対応が切れ、R5 が再演する。

## 未確定事項

- 検出述語のうち Rust regex で表現できないパターン（lookaround 等）の扱い — fancy-regex 採用か手書き述語か。R2 の全 regex 棚卸しの結果で確定する。
- lint による `format!` 制限の実現粒度は実装時に確定する。縛れない場合はレビュー基準＋ゲート (b)(c) で担保する。

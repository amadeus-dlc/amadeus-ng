# ドメインモデルの名前はユビキタス言語にする — 例外には理由が要る

**裁定日**: 2026-08-24（オーナー）
**関連**: [factory-naming.md](factory-naming.md)（生成の名前）、[gateway-taxonomy.md](gateway-taxonomy.md)（Gateway の語）、[tell-dont-ask.md](tell-dont-ask.md)
**機械強制**: なし（レビュー基準）。例外の記録は `// amadeus-lint: allow(...) <理由>` の規約と同じ精神で、**doc コメントに理由を書く**

## 原則

**ドメインモデルの型名・フィールド名・メソッド名は、ユビキタス言語（そのドメインで人が使う語）
にする。** 実装の都合から出てきた語ではなく、仕様書・設計書・オーナーとの会話に現れる語を使う。

**例外はある。ただし理由が要る。** 理由なくユビキタス言語から外れた名前は認めない。
外れるときは doc コメントに一行で理由を書く — 後から読む人が「なぜこの語なのか」を
その場で判断できるようにするため。

## 対象

「ドメインモデル」= `modules/core/domain/` の**集約・エンティティ・値オブジェクト・
ドメインイベント・ドメインサービス**。具体的には:

- 型名（`Intent` / `IntentExecution` / `IntentId` / `IntentExecutionId` / `StageSlug` / `PhaseBoundary` …。~~`WorkflowExecution`~~ → 分割・改名 2026-08-29 オーナー裁定 — **`Intent` は静的な intent の集約**（id・依頼文・scope・解決済み計画・定義参照・scan。作成時に `IntentEvent::Created` を吐き、変異は現状なし — 2026-08-30 オーナー裁定で「集約ではない構造体」の記述を上書き）、**`IntentExecution` が実行時文脈を持つ集約**（旧 WorkflowExecution の実体。cursor・checkbox・overlay・park 等 + 所有する intent）。**1 intent : n 実行**（Intent を元にIntentExecution は何回も起きる — オーナー裁定）なので実行は自前の `IntentExecutionId` を持つ。workflow の名は定義側 `WorkflowDefinition` の持ち物。旧 `WorkflowExecutionState` は `IntentExecutionSnapshot` に改名ののち、**2026-08-30 オーナー裁定で型ごと撤去** — 集約と構造同一の memento 双子は複製でしかなく、再構成は最新スナップショットと、その通番より後の差分イベントの `replay` で行う（再生方式は 2026-09-05 オーナー裁定で訂正。詳細は [aggregate-commands.md](aggregate-commands.md)））
- フィールド名（アクセサ経由で公開される名前を含む — [field-visibility.md](field-visibility.md)）
- メソッド名（コマンド・クエリの両方）
- ドメインイベントの名前とそのペイロード

## 判定

### 集約IDの型名は集約名 + `Id`（2026-09-08再確認）

利用者の明示指示により、集約ルートが `Xxx` なら、その識別子の型名は必ず `XxxId` とする。この対応規則を、一般的な命名の例外で読み替えない。

| 集約 | 集約ID型 |
| --- | --- |
| `Intent` | `IntentId` |
| `IntentExecution` | `IntentExecutionId` |
| `PlanApprovalRuntime` | `PlanApprovalRuntimeId` |

- 集約名の一部を省略したID名、保存媒体や配置から取ったID名、別名の型エイリアスで代用しない。
- 集約を改名したら、ID型、ファイル名、Repositoryの署名、イベントの集約参照、境界での変換、テストも対応させる。
- イベント自身のIDと、同じ操作を追跡する相関IDは、集約IDとは役割が異なる。集約の `id` やイベントの `aggregate_id` に、それらを流用しない。
- 全集約について「集約名・ID型・保持フィールド・Repositoryの引数型」を照合する。名前の一覧やコンパイル成功だけで適合と判定しない。

内部の型名の規則であり、監査文字列やJSONキー等の外部契約の逐語は維持する。点検結果は現在のintent記録に残す。

### その他のドメイン名

```
1. この名前は、仕様書・設計書・オーナーとの会話に出てくる語か？
   ├─ Yes → それでよい
   └─ No  → 次へ

2. ドメインの語に置き換えられるか？
   ├─ Yes → 置き換える
   └─ No  → 例外。**doc コメントに理由を一行書く**
```

## upstream の語彙は、そのままではユビキタス言語ではない

**upstream（AI-DLC 本体）は DDD で設計されていない**（オーナー明言 2026-08-24）。参考にはするが
鵜呑みにしない。したがって「upstream がこう呼んでいるから」は、それだけではドメイン語である
根拠にならない。

区別すべき 2 つ:

| | 何か | どう扱うか |
| --- | --- | --- |
| **Published Language** | 観測互換が要求する面に**現れる値** — 監査イベント文字列（`AUTONOMY_MODE_SET`）、状態ファイルのフィールド名、CLI の動詞、ワイヤ形式のキー | **逐語で維持する。** 変えると互換が壊れる |
| **Ubiquitous Language** | **我々のドメインモデル**の型名・フィールド名・メソッド名 | **我々の語でよい。** upstream に合わせる義務は無い |

**判定は「その名前は外に出るか」**。出るなら Published Language として逐語、出ないなら我々の
ドメイン語にする。`AUTONOMY_MODE_SET` という**文字列**は外に出るので逐語だが、それを発する
**メソッドの名前**は外に出ないので upstream に合わせる理由がない。

同じ理由で、upstream の関数名・変数名・モジュール名を写した命名は例外にならない。写してよいのは
**値**であって**呼び方**ではない。

## 例外として認められる典型（いずれも理由の記述が必要）

| 類型 | 例 | 書くべき理由の形 |
| --- | --- | --- |
| **Published Language の逐語** | 観測互換が要求する面に**現れる値**（監査イベント文字列・ファイル形式のキー・CLI トークン） | 「upstream `<場所>` の逐語。**外に出る値**なので変えると観測互換が壊れる」 |
| **言語・標準ライブラリの確立語** | `parse` / `encode` / `decode` / `Display` | 「Rust の確立語。ドメイン語に置き換えると読み手が身構える」 |
| **ドメインに語が存在しない技術的境界** | ワイヤ表現、シリアライズ形式 | 「ワイヤ表現であってドメインの概念ではない」 |
| **同名衝突の回避** | ドメイン語が既に別の意味で使われている | 「`<語>` は既に `<別の型>` が使っている」 |

## 禁止パターン

- 実装の都合から出た語をドメインモデルに持ち込む（`data` / `info` / `manager` / `handler` /
  `util` / `helper` / `process` / `handle`）
- **upstream の呼び方**（関数名・変数名・モジュール名）を写して「upstream 逐語だから」を
  理由にする。逐語で守るのは**外に出る値**だけである
- データ構造の語をドメインモデルのメソッド名にする（`set_` / `get_` / `update_`）—
  何が起きるのかをドメインの語で言い直せないか先に考える
- **理由を書かずに**ユビキタス言語から外れる
- 仕様書とコードで**同じ概念を別の語**で呼ぶ（どちらかに寄せる。寄せられないなら理由を書く）
- ドメインの語を**技術的な意味に流用**する（同じ語が 2 つの意味を持つと会話が壊れる）

## 運用 — 規則を書いたら、その場で全体を掃く

新しい命名規則を正本に書いたら、**スコープを切る前にリポジトリ全体を掃いて違反を洗い出す**。
「誰が書いたコードか」「どの Unit か」で先に線を引くと、規則自身が名指しする違反が視界から
外れる（2026-08-24 の実例: ファクトリ命名で U3 の 2 件だけ直し、既存の 6 件をオーナーに
指摘されるまで見落とした）。切るのは全件が机に載ってからでよい。

## 対象外

- `modules/core/interface-adapter/` 以下のワイヤ表現・行マッピング（技術的境界であり
  ドメインモデルではない）。ただし**ドメインの語を写す部分は語を保つ**こと。
- infrastructure の汎用モジュールと境界の文言モジュール（`core_infrastructure::canon_json` / 各出し手の `wording` — 2026-08-29 の shared 解体で移設）。これらは
  ドメインを持たない汎用部品である。
- `modules/infra-io/` の I/O プリミティブ。

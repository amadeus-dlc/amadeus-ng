# 借り物の契約を自分のドメインに合わせて曲げない

**裁定日**: 2026-08-26（オーナー）
**土台**: [abstract-data-type.md](abstract-data-type.md)（契約にだけ依存する）
**関連**: [ubiquitous-language.md](ubiquitous-language.md)（Published Language）、
[gateway-taxonomy.md](gateway-taxonomy.md) §1c（永続化基盤ポート）
**機械強制**: 無し（レビュー基準）

## 原則

**外部ライブラリ・upstream の契約（trait・型・シグネチャ）を、自分のドメインに合わせて
改変してはならない。ライブラリには**別のドメイン**がある**（オーナー明言 2026-08-26
「ライブラリなのに、当該ドメインに影響受けるのはもってのほか」「ドメインが違うんだよ」）。

DDD の語で言えば、外部ライブラリは**上流の境界づけられたコンテキスト**である。取りうる関係は
2 つしかない。

| 関係 | 中身 | いつ選ぶか |
| --- | --- | --- |
| **Conformist（従属）** | 相手の言語をそのまま受け入れる。契約は 1 文字も変えない | 相手の語彙が素直で、翻訳のコストが利得を上回るとき |
| **腐敗防止層（ACL）** | 境界に変換層を置き、内側は自分の言語を保つ | 相手の語彙が自分のドメインを歪めるとき |

**契約のほうを書き換えるのは、このどちらでもない壊れた折衷である。** 見た目は Conformist だが
中身が違うので、乗り換え・合流・upstream 貢献のすべてが成立しなくなる。

## 判定

```
外部の契約と自分のドメイン型が食い違った
├─ 契約を変える            → 禁止。それは相手のドメインへの侵入である
├─ 自分のドメインを変える  → 相手の語彙が本当に自分のドメインでも正しいときだけ。
│                            「合わせるため」は理由にならない
└─ 境界で変換する          → **既定の答え**。ドメインは自分の型を保ち、
                             アダプタが相手の型へ写す
```

境界での変換は暴露ではなく**変換**である（[abstract-data-type.md](abstract-data-type.md)
§境界での変換）。変換関数には C-CONV の綴りを使う（`to_u64` / `to_usize`）。

## 外部 trait の実装は、こちらの命名規則の例外である

Conformist で外部 trait を実装すると、**相手の契約が決めたメソッド名**をこちらの型に
生やすことになる（実例: `AggregateId::value()` — 我々の
[tell-dont-ask.md](tell-dont-ask.md) は自前アクセサに `value()` を禁じているが、
外部 trait の実装は **Published Language への準拠**であり例外）。impl の doc コメントに
一行、外部 trait 準拠である旨を書く。**例外なのは trait が要求するメソッドだけ**で、
同じ型の自前メソッドには引き続きこちらの規則が全面適用される。

## 「同形でローカル定義」する場合はさらに厳しい

依存の重さなどの理由で、外部 crate に依存せず**同形の trait をローカル定義する**ことがある
（本リポジトリの ADR-006 がこれ）。この場合、同形性は**手動で維持するしかない**ので、
次を守る。

- **ローカル定義を「自分の契約」と思わない。** それは相手の契約の写しであり、所有者は相手である
- **写しを自分の都合で変えない。** 変えた瞬間、乗り換え可能性という当初の目的が消える
- **本家の更新を定期的に確認する。** 「同形」は時間とともに劣化する
- 差分が必要なら、**ADR に理由を残す**（同形性を捨てる裁定は明示的に行う）

## 実行時に出す指示の綴りも、借り物の契約である（2026-09-22 裁定）

**裁定日**: 2026-09-22（オーナー）

native が実行時に出す指示 — エンジンの directive の本文、フックや拒否文言が案内する
コマンド — は、**本家 aidlc の Published Language** である。読み手は本家の指示に慣れた
コンダクタであり、綴りが違えば指示に従えない。したがって関係は **Conformist** であり、
本家をコンパイル済み実行形で動かしたときの出力に**逐語一致**させる。綴りを推測しない。

**この原則は、本家の綴りが我々の都合に反するときにも曲げない。** 実例として、本家
2.8.2 の `continue-workflow` フックは案内文に `bun .claude/tools/aidlc-orchestrate.ts`
を綴る（同梱 `.claude/hooks/aidlc-continue-workflow.ts:1179,1190,1194`）。native は
配布版 TypeScript を起動させない方向へ進んでいるので、この綴りは我々にとって望ましくない。
それでも**本家が出す綴りをそのまま出す**のが正しい。望ましくないという理由は、相手の
契約を書き換える理由にならない（§判定の「自分のドメインを変える」参照 —「合わせるため」は
理由にならないのと同じく、「合わないから」も理由にならない）。

本家から意図的に乖離する場合は、他の契約と同じ扱いにする。**ADR に理由を残し、上流へ
報告する。** 黙って綴りを変えるのが、最も壊れた選択である。

実装上の帰結:

- 綴りの組み立ては 1 か所に集約する（`dispatcher_invocation` /
  `EngineCommand::cli_spelling`）。生成箇所ごとに文字列を手で綴らない
- 本家自身が別の綴りを出す箇所は、**出典つきの例外**として登録する
  （`runtime_directive_contract.rs` の `ALLOWED_LITERALS` が `upstream_file` /
  `upstream_marker` とともに固定している）
- 出典の無い例外は認めない。例外が増えたら、それは本家の版が上がった合図である

## 失敗の実例（2026-08-26 記録）

本リポジトリで実際に起きた。**同じ失敗を繰り返さないために残す。**

1. ADR-006 が「`event-store-adapter-rs` と**同形で**ローカル定義し、**乗り換え可能な形を保つ**」
   と決めた（見送り理由は依存の重さ。乗り換え条件は「本家が feature 化 / SQLite 実装を得たら」）
2. U3 の実装で、集約の `seq_nr` / `version` が `u64` だったため、**契約側の `usize` を `u64` へ
   「具体化」した**。判断の基準は「自分のドメイン型に合わせる」だった
3. functional-design も、2 回のレビューも、コンダクタも、**誰も「本家が `usize` なのに我々が
   変えてよいのか」を問わなかった**。全員が「実装が正、契約が古い」という前提で動いた
4. 2026-08-24、本家 v2.0.0 が **feature ゲート化と SQLite 実装**を同時にリリース。
   ADR-006 の乗り換え条件が両方とも満たされた
5. その時点で、我々の契約は本家と 4 点ずれていた（関連型 vs 型パラメータ / `usize` vs `u64` /
   エラー型 1 種 vs 2 種 / `Clone` 境界の有無）

**教訓**: 契約の所有者が誰かを、変更の直前に必ず確認する。「実装が正、契約が古い」は
**自分が契約の所有者であるときにだけ**成り立つ。

> **位置づけ**: 本書は amadeus-ng 仕様セット（`docs/specs/`）の最初の文書であり、以後のすべての仕様と実装が従う決定を記録する。

> **策定日**: 2026-08-22。根拠は upstream 仕様 13 本の全数分析（2026-08-21 実施、13 並列精査＋横断批評）。

## 1. 確定した決定

amadeus-ng は、aidlc-workflows（TypeScript + bun 実装）を Rust で再実装するプロジェクトである。以下の 8 点を確定事項とする。

| # | 決定 | 内容 |
| --- | --- | --- |
| D1 | 実装言語 | Rust。ユーザー環境のランタイム前提（bun）を排し、プリビルドバイナリで配布する。 |
| D2 | 仕様の構造 | ドメインモデル起点で新規に書く。upstream 13 本はサブシステム別の as-built 仕様として凍結参照し、書き換え対象にはしない。 |
| D3 | ドメインモデルの流儀 | Always Valid Domain Model / Domain Primitive を採用する。不正な状態は型で表現不能にし、検証は境界（パース時）で行う。 |
| D4 | アーキテクチャ | クリーンアーキテクチャを踏襲する。ドメイン層 → ユースケース層 → インターフェイスアダプタ層（Gateways / Controllers / Presenters）の 3 層は依存が常に内向き。横断の**インフラストラクチャ層**は 2 群に分ける: **純粋部品**（正準 JSON・文言カタログ・ハッシュ等）は 3 層のどこからでも利用可、~~**infra-io**（アトミック書込・spawn 基盤・テレメトリ配線）~~ → **失効（2026-08-29 / Bolt B8）**: `core-infrastructure`（`modules/core/infrastructure` — 旧 infra-io の改名。言語拡張のみを置き RPC/DB アクセスは置かない）に改名・移動した。加えて harness 文脈向けの `harness-infrastructure`（`modules/harness/infrastructure`）を新設。両クレートとも「どの層も知らない・どの層からも使ってよい」層外の位置づけは Gateways を含むアダプタ層と composition root のみが依存できるという原則ごと不変（`crate-structure-proposal.md` §1）。**I/O の責務（ファイル・プロセス・git・ネットワーク/RPC・データソース）は Gateways が担う**。各層は独立 Cargo クレートで逆依存はビルドエラー。詳細は `01-domain-model.md` §7。 |
| D5 | 初期スコープ | Claude Code 1 ハーネス＋決定論コアの縦切り。センサー・プラグイン・他 6 ハーネス・配布パイプライン一般化は後続フェーズ。 |
| D6 | 命名・互換（初期フェーズ） | aidlc 互換を維持する。範囲の定義は §2 を参照。amadeus ブランドへの全面改名は stage-1 安定後に改めて判断し、それまで逸脱台帳に保留として記録する。 |
| D7 | 仕様書の言語 | 日本語正本のみ。upstream 流の英語正本＋ `.ja.md` 対訳体制は採らない（凍結済み upstream 参照は英語のまま）。 |
| D8 | 開発戦略 | ブートストラップ（ホスト/ターゲット方式）。詳細は §4。 |
| D9 | 形式仕様 | Quint を決定論コアの状態機械契約に適用する。仕様内部の矛盾（ゲート迂回トレース、デッドロック、両立不能な不変条件）を実装前に検出する。適用範囲と運用は A9 で確定する。 |
| D10 | 実装進行 | **ドメインモデルから作る**（ドメインモデルに駆動されるシステムにするための必須条件）。機能・ユースケースを想定しつつも、各コンテキストの Domain Primitive・集約・ドメインサービスを **TDD**（red-green-refactor）で先行実装し、ドメイン層の型が安定してからユースケース → アダプタ → インフラを外側へ重ねる（inside-out）。 |

D3・D4 は Rust と相性がよい。newtype と enum で Domain Primitive を表現し、所有権で集約境界を守り、trait でレイヤー間の依存逆転を実現できる。D9 は D3 と一本のパイプラインになる — 境界に置く不変条件を先に Quint の不変条件として書いて模型検査し、通ったものを newtype / enum に落とす。なお Quint が検出するのはモデル化した状態機械の中の矛盾であり、散文レベルの矛盾（逐語文言のずれ、Markdown 契約同士の食い違い）は対象外。そちらは文言カタログ（A3）・逸脱台帳・相互参照レビューで守る。

## 2. D6 の互換範囲 — どこまで aidlc 互換か

「互換」の範囲を先に定義しておかないと、実装の途中で判断がぶれる。初期フェーズの互換対象は次のとおり。

**互換を維持するもの（意味論＋表現の両方）**:

- ワークスペースレイアウト（`aidlc/spaces/<space>/intents/…`）と状態ファイル `aidlc-state.md` の文法
- 監査ログの形式とイベント語彙（86 イベントのタクソノミ）
- CLI のサブコマンド語彙・JSON エンベロープ・exit code 契約
- 環境変数名（`AIDLC_*`）
- LLM エージェントの分岐条件になっている逐語文言（エラーメッセージ、拒否文言、ゲート文言）
- ステージ・エージェント・プロトコルの Markdown 資産（upstream からほぼ逐語で引き継ぐ）

**互換対象外とするもの**:

- 起動配線。upstream の hooks.json や設定には `bun <path>.ts` という起動コマンドが焼き込まれているが、Rust 版に bun は存在しないため、ここは `aidlc <tool> <サブコマンド>` 形式のバイナリ呼び出しに置換する。Markdown 資産中のコマンド綴りも同じ写像で置換する（upstream の T5 トークン置換と同種の、パッケージング時の機械的変換として実装する）。
- 開発側ツールチェーン（tsc/biome/bun test → cargo check/clippy/cargo test）。ユーザーには見えない。

この「コマンド綴りの写像」は逸脱第 1 号として逸脱台帳に記録する。互換維持の検証は、upstream の実出力・実ワークスペースをゴールデン入力とする差分テストで行う（§6 R7〜R9）。

**判定原則（2026-08-22 オーナー裁定）**: 互換の判定は常に「**仕様**か**実装**か」で行う。仕様＝観測可能な契約（オンディスク形式、監査行、逐語文言、CLI 面での振る舞い、原子性の保証）は踏襲必須。実装＝内部機構（プロセス構成、ライブラリ選定、アルゴリズム）は、仕様を守る限り最適なものを選んでよく、**本家実装の模倣は要件ではない**。仕様への準拠はゴールデン互換層で証明する。逸脱台帳に載るのは仕様レベルの逸脱のみで、仕様を破らない実装選択は各仕様書の「実装ノート」節に記録する。

## 3. これから決めること — ADR の依存順序

横断批評が指摘したとおり、次の決定群は各仕様に先行して一度だけ確定させる必要がある。個別仕様の中でその都度決めると、13 本の分析ですでに観測されたのと同じ「仕様間で推奨が割れる」事態が再現するからだ。ADR は `docs/adr/` に連番で置く。

| # | 決定事項 | 要点 |
| --- | --- | --- |
| A1 | 配布モデルの詳細 | 単一マルチコールバイナリ＋資産ツリーを推奨案とする。バイナリと資産のバージョンハンドシェイク（スキュー検出と doctor 照合）を初版から設計する。**配布チャネルは `cargo install` / `cargo install --locked`（更新も同経路）を一級とし、バイナリ自身が資産インストーラのサブコマンド**（upstream の「dist ツリー再コピー」に相当する配置・更新・doctor 照合）**を持つ**（2026-08-22 オーナー決定。本家にインストーラは無く「再コピーが運用契約」なので、追加機能として逸脱台帳の拡張分類に記録。インストール後のワークスペース形状は dist コピー結果と一致させる）。 |
| A2 | 正準 JSON シリアライザ | 全 crate が共有する単一の決定的シリアライザを最初に固定する。ハッシュ・ドリフトガード・冪等判定のすべてがこの上に乗る。 |
| A3 | 文言カタログ | 逐語文言とコマンド語彙を単一の定数モジュールに集約し、生成側と検出側（ガードパーサ等）が同一カタログを参照する。upstream 逐語の写しとして管理する。 |
| A4 | プロセス実行基盤 | spawn ユーティリティの一本化（sync か tokio か、timeout エスカレーション、プロセスグループ）、exit code レジストリ、panic ポリシー（`process::exit` は明示クリーンアップ経由のみ、フック入口の catch_unwind、clippy の disallowed_methods で強制）。 |
| A5 | タイムスタンプと文字列単位の契約表 | ISO-8601 の受理集合（JS `Date.parse` と chrono の差）、長さ・切詰・ソートの単位（JS UTF-16 / Rust byte）を契約ごとに明記した対応表。 |
| A6 | マニフェスト形式 | TOML＋serde を推奨案とする。upstream の `emit()`（任意 TS コード）は組み込み emitter trait に置換。「ハーネス追加はビルドエントリ編集ゼロ」の約束との緊張を記録して判断する。 |
| A7 | upstream 追従戦略 | CHANGELOG エントリ単位の定期 diff レビュー、逸脱台帳（upstream 挙動 / amadeus 挙動 / 理由 / 分類）による一元管理、追従を打ち切る条件。 |
| A8 | リポジトリ構成 | **確定済み（ADR 0005）**: モノレポ（main に docs とコード同居）。~~`modules/{core,shared,infra-io,app,harness}` 構成~~ → **失効（2026-08-29 / Bolt B8。同日中の是正を in-place 反映）**: `infra-io` は `modules/core/infrastructure`（`core-infrastructure`）へ改名・移動し、`modules/harness/infrastructure`（`harness-infrastructure`）が新設された。現行構成は `modules/{core,shared,app,harness}`（`core` 配下は `command/{domain,use-case,interface-adapter}`（コマンド側 3 クレート — ドメインはコマンド側の持ち物）・`read-model-updater`（RMU。コマンド側でもクエリ側でもない**中間** — 側接頭辞なし）・`infrastructure` に分かれる。`query/` サブディレクトリは存在しない — 詳細は `coding-rules/cqrs-boundaries.md`、`crate-structure-proposal.md` §1）。層＝クレートで逆依存はビルドエラー、コンテキストは当面モジュール（最初の切り出しは verification 述語クレート）。ライセンスは `MIT OR Apache-2.0` デュアルを workspace 既定に設定。 |
| A9 | Quint の適用範囲と運用 | 対象はオーケストレーション（最優先: intent ライフサイクル × `next`/`report`、jump/park/resume、ゲート）、ロック/監査（クラッシュをアクションに含めた並行モデル）、フック/センサー判定（フェーズ C）に絞る。ステージグラフのコンパイル不変条件は状態遷移ではないため Rust の proptest で足りる見込み。モデルの配置、CI ゲート（毎 PR は `quint run` のシミュレーション、Apalache による `quint verify` はエンジン変更時と nightly）、ITF トレース準拠層の設計をここで確定する。 |
| A10 | 可観測性（OTel） | **確定済み（ADR 0004）**: 計装は `tracing`、エクスポートは OpenTelemetry。監査台帳が真実源で、テレメトリは派生（append 成功後 emit、fail-open）。トレース境界は 1 ターン = 1 トレース（prompt-submit / Stop フックがターンコンテキストを発行・クローズ）、エクスポートは flush 方式で開始し較正で detached ワーカーへエスカレート可。 |

決定の順序は A8 → A1 → A3 → A2 → A4/A5/A6 → A7 を基本とする。A8 と A1 が他のすべての前提になる。A9 は他と独立に決められるが、最初のモデルをオーケストレーション・コンテキスト仕様と同時に書くため、その着手前までに確定させる。

なお A2・A3・A9・A10 は「D6 で凍結済みの upstream 資産に対する契約」という性格上 A8/A1 と独立に規範を定められるため、ADR 0001〜0004 として先行確定した。クレート名・配置など A8 依存の細目はそれらの ADR では非規範とし、A8 確定時に追認する。A3（ADR 0002）の写像表は A1 への依存（ディスパッチャ語彙の提供）を明示しており、A1 の ADR はこれを引き受ける。

## 4. 開発戦略 — ブートストラップ（D8 の詳細）

コンパイラの stage-0/stage-1 と同じ構図を採る。amadeus-ng の成果物は「開発ワークフローを回す装置」そのものなので、自分の開発に使うことが最良の受入テストになる。

**stage-0（現在〜初期版完成）**: upstream の `dist/claude/` を amadeus-ng のコードリポジトリに導入し、本家 AI-DLC ワークフローをホストとして amadeus-ng を開発する。セットアップはプロジェクトオーナーが実施する（bun のインストールと、非対話シェルの PATH 問題 — bun インストーラは `~/.zshrc` に書くがフックは `~/.zshenv` を読む — に注意。upstream 00-overview §7.1）。

**stage-1（切替）**: 初期版 amadeus-ng が下の条件を満たしたら、ホストを amadeus-ng に差し替え、以後は自己開発（セルフホスト）に移行する。

切替条件は次の 5 点とし、センサーとプラグインは含めない。

1. エンジン `next` / `report` が Claude Code 上でゲート込みで動く
2. 状態・監査・ロックが upstream 互換で機能する（D6 の範囲）
3. 自プロジェクトの開発で使うスコープ（bugfix / feature 相当)のステージ一式が揃っている
4. `--doctor` 自己診断が green
5. smoke + unit 相当の CI が green

**self-hosting tax への対策**: 切替後は「ホスト＝直近の安定タグ、ターゲット＝開発版」の 2 版運用とする。開発版の不具合で自分の開発が止まったら、git でホストを前の安定タグに戻す。D6 で互換維持を選んだため、切替時のワークスペース移行は原則不要になる（これが D6 を初期フェーズの選択とした主な理由でもある）。

## 6. リスク台帳

分析の横断批評で挙がった、Rust 化で特に失敗しやすい点。各仕様・各 ADR はここを踏まえて書く。

| # | リスク | 手当て |
| --- | --- | --- |
| R1 | 正準 JSON の仕様間分裂（分析段階ですでに 5 通りの推奨が併存） | A2 で最初に一本化 |
| R2 | JS RegExp と Rust regex の意味論差（lookaround 非対応、`\b` や `i` フラグの Unicode 挙動差）による受理集合の静かな乖離 | upstream の全 regex を棚卸しし、パターンごとに受理/拒否のゴールデン表を作る |
| R3 | Windows 対応の仕様間矛盾（POSIX 前提の防御機構が未定義のまま Windows バイナリだけ出荷される「動くが守られていない」ビルド） | 初期フェーズは macOS / Linux のみと明記。Windows はフェーズ D 以降で防御の等価物定義とセットで |
| R4 | バイナリ×資産のバージョンスキュー（upstream は dist 再コピーで原子的に一致していた） | A1 のバージョンハンドシェイク＋doctor 照合 |
| R5 | 逐語文言・コマンド綴り置換の非原子性（置換漏れ 1 箇所が LLM エージェントの静かな挙動破壊になる） | A3 の文言カタログ＋旧綴り（`"bun "` 起動形・`.ts`）残骸を grep する CI ゲート |
| R6 | `process::exit` がデストラクタを走らせない（Bun の「exit 時 finally スキップ」と同型の罠）、panic が「フックは fail-open」契約を破る | A4 の規約と clippy 強制。加えてクラッシュをアクションに含めた Quint ロックモデルで「全経路でロック解放」を検査（A9） |
| R7 | ダイジェスト計算の不一致による冪等ガードの誤発火（TS 版が書いたワークスペースを開いた瞬間に「変化あり」と誤検知） | ダイジェスト計算も互換対象とし、upstream 実ワークスペースを食わせる互換テストで固定。「既知形式だがダイジェスト不一致」時の安全側挙動を契約化 |
| R8 | `Date.parse` の寛容さを chrono で機械置換すると受理集合が変わる | A5 の契約表＋upstream 実データのゴールデン |
| R9 | 忠実サブセットパーサ（YAML サブセット、行ベース Markdown）を serde_yaml や pulldown-cmark に置き換えたくなる引力。往復忠実性・寛容パース＋具体的拒否文言という契約が静かに変わる | 手書き再実装を規定。33 ステージ全量＋実ワークスペースをゴールデン入力とする差分テストを先に整備。汎用パーサへの置換は逸脱台帳マター |

## 7. その他の細目

- **ライセンス**: upstream は MIT-0（帰属義務なし）のため、派生物である amadeus-ng を別ライセンスで公開することに法的障害はない。amadeus-ng 自身は **Apache-2.0 または MIT を予定**（Rust エコシステム慣習の「MIT OR Apache-2.0」デュアルライセンスも含め、コードリポジトリ作成時 = A8 確定時に最終決定する）。いずれの場合も NOTICE 相当のファイルで出自（awslabs/aidlc-workflows、対象コミット 3c3146cf）を明記する。トレーサビリティと礼儀のため。
- **検証戦略（三層）**: (1) **ゴールデン互換層** — upstream 実出力・実ワークスペースを固定入力とする互換テスト。TS 版と同じ振る舞いか（R2・R7〜R9 の受け皿）。(2) **モデル検査層** — Quint による決定論コアの模型検査。仕様自体が内部矛盾していないか（D9）。(3) **モデル準拠層** — Quint が生成する ITF トレース（Informal Trace Format、JSON）を `itf` クレート（リポジトリ名は informalsystems/itf-rs）で読み、Rust エンジンに再生して突き合わせる準拠テスト。実装がモデルどおりに振る舞うか。ユニットテスト自体は upstream の 4 層（smoke / unit / integration / e2e）を cargo test で踏襲し、**単体テストは基本 PBT（proptest）で書く**（2026-08-22 オーナー規約 — 例示テストはユビキタス言語の文書化として併用可。集約にはランダムコマンド列に対する Quint 不変条件の Rust 版検査を置く）。LLM 依存テストの CI 運用（鍵・コスト・flake）はフェーズ B 以降に ADR 化する。
- **Quint のツールチェーン**: npm 配布の開発側ツール（ローカルにインストール済み）。ユーザー側ランタイム排除（D1）は配布物の話であり、開発専用依存とは矛盾しない（upstream がドキュメントビルドに Python を使うのと同じ扱い）。
- **ドメインモデルの管理**: ユビキタス言語は各コンテキストの `CONTEXT.md`（用語集）として実装リポジトリにも置き、仕様書と二重化しない運用を検討する（`01-domain-model.md` 策定時に確定）。
- **設計スキルの標準装備**: オーナー作の software-design プラグイン（[j5ik2o/ai-tools](https://github.com/j5ik2o/ai-tools/tree/main/plugins/software-design)、29 スキル）を開発環境の標準装備とする。D3（Always Valid / Domain Primitive / parse-don't-validate）・D4（クリーンアーキテクチャ）・D10（ドメインモデル先行）を仕様執筆と実装セッションの双方で運用に落とす手段であり、コピーではなくプラグイン参照で導入して単一ソース（ai-tools リポジトリ）を維持する。

# ドメインモデルの名前はユビキタス言語にする — 例外には理由が要る

**裁定日**: 2026-08-24（オーナー）
**関連**: [factory-naming.md](factory-naming.md)（生成の名前）、[gateway-taxonomy.md](gateway-taxonomy.md)（Gateway の語）、[tell-dont-ask.md](tell-dont-ask.md)
**機械強制**: なし（レビュー基準）。例外の記録は `// amadeus-lint: allow(...) <理由>` の規約と同じ精神で、**doc コメントに理由を書く**

## 原則

**ドメインモデルの型名・フィールド名・メソッド名は、ユビキタス言語（そのドメインで人が使う語）
にする。** 実装の都合から出てきた語ではなく、仕様書・設計書・オーナーとの会話に現れる語を使う。

**例外はある。ただし理由が要る。** 理由なくユビキタス言語から外れた名前は認めない。
外れるときは doc コメントに一行で理由を書く — 後から読む人が「なぜこの語なのか」を
その場で判断できるようにするため。

## 対象

「ドメインモデル」= `modules/core/domain/` の**集約・エンティティ・値オブジェクト・
ドメインイベント・ドメインサービス**。具体的には:

- 型名（`WorkflowExecution` / `IntentId` / `StageSlug` / `PhaseBoundary` …）
- フィールド名（アクセサ経由で公開される名前を含む — [field-visibility.md](field-visibility.md)）
- メソッド名（コマンド・クエリの両方）
- ドメインイベントの名前とそのペイロード

## 判定

```
1. この名前は、仕様書・設計書・オーナーとの会話に出てくる語か？
   ├─ Yes → それでよい
   └─ No  → 次へ

2. ドメインの語に置き換えられるか？
   ├─ Yes → 置き換える
   └─ No  → 例外。**doc コメントに理由を一行書く**
```

## 例外として認められる典型（いずれも理由の記述が必要）

| 類型 | 例 | 書くべき理由の形 |
| --- | --- | --- |
| **upstream 互換の逐語** | upstream の綴りをそのまま写す必要がある識別子・トークン | 「upstream `<場所>` の逐語。変えると観測互換が壊れる」 |
| **言語・標準ライブラリの確立語** | `parse` / `encode` / `decode` / `Display` | 「Rust の確立語。ドメイン語に置き換えると読み手が身構える」 |
| **ドメインに語が存在しない技術的境界** | ワイヤ表現、シリアライズ形式 | 「ワイヤ表現であってドメインの概念ではない」 |
| **同名衝突の回避** | ドメイン語が既に別の意味で使われている | 「`<語>` は既に `<別の型>` が使っている」 |

## 禁止パターン

- 実装の都合から出た語をドメインモデルに持ち込む（`data` / `info` / `manager` / `handler` /
  `util` / `helper` / `process` / `handle`）
- **理由を書かずに**ユビキタス言語から外れる
- 仕様書とコードで**同じ概念を別の語**で呼ぶ（どちらかに寄せる。寄せられないなら理由を書く）
- ドメインの語を**技術的な意味に流用**する（同じ語が 2 つの意味を持つと会話が壊れる）

## 対象外

- `modules/core/interface-adapter/` 以下のワイヤ表現・行マッピング（技術的境界であり
  ドメインモデルではない）。ただし**ドメインの語を写す部分は語を保つ**こと。
- `modules/shared/` のライブラリ（`canon-json` / `message-catalog` など）。これらは
  ドメインを持たない汎用部品である。
- `modules/infra-io/` の I/O プリミティブ。

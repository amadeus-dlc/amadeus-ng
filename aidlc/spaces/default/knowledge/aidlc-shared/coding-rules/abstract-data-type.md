# 抽象データ型 — 内部構造を暴露せず、契約にだけ依存させる

**裁定日**: 2026-08-24（オーナー）
**性格**: **土台**。他の複数の規則がここから導かれる（下記「ここから導かれる規則」）
**関連スキル**: `j5ik2o-ddd-domain-primitives-and-always-valid`、`j5ik2o-ddd-domain-building-blocks`
**機械強制**: 部分的（`cargo lint` の `no-public-fields`。それ以外はレビュー基準）

## 原則

**AVDM（Always Valid Domain Model）と DP（Domain Primitive）は抽象データ型である**
（オーナー明言 2026-08-24）。抽象データ型は**操作（契約）で定義され、表現では定義されない**。

したがって:

- **内部構造を暴露してはならない。** 暴露した時点で「表現で定義された型」に落ちる
- **呼び手はインターフェイス（契約）にだけ依存するように設計する。** 呼び手が表現を知っている
  なら、表現を変えるたびに呼び手が壊れる — それは抽象化されていない

「private にしておく」は結果であって目的ではない。目的は**呼び手が表現を知らずに済むこと**である。

## カプセル化の単位は `struct` であって `mod` ではない（オーナー明言 2026-08-24）

**Java のクラスと同じく、`struct` がモジュールの最小単位である。** `mod` を単位と見なすと、
「同一クレート内の実装詳細だから `pub(crate)` でよい」が自然に見えてくる。これは**悪魔の
ささやき**である — それを認めるなら **private の存在意義とは何か**。

そして `mod` を単位と見ると、設計が**自由関数の集まり**へ流れる。型が振る舞いを持たず、
`mod` に手続きが並ぶ形になり、**Rust らしさが減る**（型で不変条件を守る言語なのに、
手続き型の書き方に落ちる）。

### Rust の事情 — private は「モジュール内」であって「struct 内」ではない

Rust のフィールド private は**定義モジュールとその子孫**から見える。同じ `mod` に別の型を
置けば、その型からフィールドが見える。素の Rust は `mod` 単位のカプセル化なのである。

したがって **`struct` を単位にするには「1 モジュール（1 ファイル）1 struct」にする**。
そうして初めて「モジュール private ≒ struct private」が成立する。
（[module-visibility.md](module-visibility.md) の「mod はデフォルト private、公開は
ファサードの `pub use` 経由」と組み合わせて効く。）

### 帰結

- **フィールドのデフォルトは private。同一クレートでも公開しない。**
  必要最低限しか公開しない（[field-visibility.md](field-visibility.md)）
- **`pub(crate)` は「カプセル化の単位をクレートと取った」という告白**である。
  クレートは単位ではない
- 値オブジェクト・エンティティは **1 ファイル 1 型**で置く
- **自由関数の集まりになっているモジュールは設計の合図**。その手続きが本当は
  どの型の振る舞いなのかを問う

本リポジトリの実例: 値オブジェクトは `stage_slug.rs` / `intent_id.rs` / `phase.rs` … と
1 ファイル 1 型で揃っており正しい。逆に `domain/src/workspace/state_writers.rs` は
`&str -> String` の自由関数が並ぶモジュールで、まさに「`mod` を単位と見た結果、全部単体の
fn に落ちた」形になっている（`code-summary` §7 に申し送り済み — 命名だけでなく、
その手続きがどの型の振る舞いなのかから問い直す）。

## 判定 — 呼び手は何に依存しているか

```
呼び手はこの型の「何」に依存しているか？
├─ 操作（メソッド）だけ            → 抽象データ型として成立している
└─ 表現（中身の型・構造）にも依存   → 暴露している。契約側へ移す
```

「型は private だがアクセサで中身をそのまま返している」は**暴露である**。可視性修飾子ではなく、
**呼び手が何を知っているか**で判定する。

## 境界での変換は暴露ではない

抽象データ型でも、**外の世界と接する境界**ではプリミティブへ降りる必要がある — 索引計算、
ワイヤ表現、外部 API。これは暴露ではなく**変換**であり、C-CONV に従って変換として名乗る
（`as_str` / `to_usize` / `to_u64`）。

暴露と変換の違いは名前ではなく**必要性**にある。

- **変換**: 境界を越えるために必要で、越えた先ではもうその型ではない
- **暴露**: 呼び手が中身を取り出して**自分で判断する**ために使っている。判断は型の側にあるべき

したがって「`value()` を `to_usize()` に改名した」だけでは足りない。**その呼出が本当に境界の
変換なのか、判断の持ち出しなのか**を 1 件ずつ見る必要がある。

## 禁止パターン

- 内部型を返すだけのアクセサ（`value()` / `inner()` / `raw()` / `get()`）
- `pub` / `pub(crate)` フィールド
- 呼び手が中身を取り出して条件分岐する（判断を型へ移す）
- 表現の変更が呼び手を壊す設計（= 契約に依存していない証拠）
- 「テストのため」に表現を公開する（テストも契約経由で書く。書けないなら契約が足りない）

## 対象外

- **ワイヤ表現の型**（`interface-adapter/src/orchestration/wire/`）— 外部形式の写しであって
  ドメインの抽象データ型ではない。ただしドメイン型へ写す境界では、ドメイン側の契約に従う
- `modules/shared/` の汎用ライブラリ（`canon-json` など）— ドメインを持たない部品

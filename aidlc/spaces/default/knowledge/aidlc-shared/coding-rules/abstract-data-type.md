# 抽象データ型 — 内部構造を暴露せず、契約にだけ依存させる

**裁定日**: 2026-08-24（オーナー）
**性格**: **土台**。他の複数の規則がここから導かれる（下記「ここから導かれる規則」）
**関連スキル**: `j5ik2o-ddd-domain-primitives-and-always-valid`、`j5ik2o-ddd-domain-building-blocks`
**機械強制**: 部分的（`cargo lint` の `no-public-fields`。それ以外はレビュー基準）

## 原則

**AVDM（Always Valid Domain Model）と DP（Domain Primitive）は抽象データ型である**
（オーナー明言 2026-08-24）。抽象データ型は**操作（契約）で定義され、表現では定義されない**。

したがって:

- **内部構造を暴露してはならない。** 暴露した時点で「表現で定義された型」に落ちる
- **呼び手はインターフェイス（契約）にだけ依存するように設計する。** 呼び手が表現を知っている
  なら、表現を変えるたびに呼び手が壊れる — それは抽象化されていない

「private にしておく」は結果であって目的ではない。目的は**呼び手が表現を知らずに済むこと**である。

## 判定 — 呼び手は何に依存しているか

```
呼び手はこの型の「何」に依存しているか？
├─ 操作（メソッド）だけ            → 抽象データ型として成立している
└─ 表現（中身の型・構造）にも依存   → 暴露している。契約側へ移す
```

「型は private だがアクセサで中身をそのまま返している」は**暴露である**。可視性修飾子ではなく、
**呼び手が何を知っているか**で判定する。

## 境界での変換は暴露ではない

抽象データ型でも、**外の世界と接する境界**ではプリミティブへ降りる必要がある — 索引計算、
ワイヤ表現、外部 API。これは暴露ではなく**変換**であり、C-CONV に従って変換として名乗る
（`as_str` / `to_usize` / `to_u64`）。

暴露と変換の違いは名前ではなく**必要性**にある。

- **変換**: 境界を越えるために必要で、越えた先ではもうその型ではない
- **暴露**: 呼び手が中身を取り出して**自分で判断する**ために使っている。判断は型の側にあるべき

したがって「`value()` を `to_usize()` に改名した」だけでは足りない。**その呼出が本当に境界の
変換なのか、判断の持ち出しなのか**を 1 件ずつ見る必要がある。

## 禁止パターン

- 内部型を返すだけのアクセサ（`value()` / `inner()` / `raw()` / `get()`）
- `pub` / `pub(crate)` フィールド
- 呼び手が中身を取り出して条件分岐する（判断を型へ移す）
- 表現の変更が呼び手を壊す設計（= 契約に依存していない証拠）
- 「テストのため」に表現を公開する（テストも契約経由で書く。書けないなら契約が足りない）

## 対象外

- **ワイヤ表現の型**（`interface-adapter/src/orchestration/wire/`）— 外部形式の写しであって
  ドメインの抽象データ型ではない。ただしドメイン型へ写す境界では、ドメイン側の契約に従う
- `modules/shared/` の汎用ライブラリ（`canon-json` など）— ドメインを持たない部品

## 原則

リードモデル更新器（RMU の `…ReadModelUpdater`）の構造を、オーナー裁定 1〜6 として定める。

### 1. 論理構造 — 読む・投影する・DAO で書く、だけ

更新器がするのは「**ジャーナルを読む → 投影（純粋な変換）→ DAO でリードモデルを更新する**」だけである。
`ReadModelWriter` のような大きな書き込みポートは作らない（オーナー「ReadModelWriter は不要。DAO があるから」）。

```text
                ┌──────────────── 更新器 (…ReadModelUpdater) ────────────────┐
                │                                                           │
 journal ──▶ JournalReader ──▶ 事実 ──▶ 投影 (純粋) ──▶ 行 ──▶ 表の DAO ──▶ 表 A
 (1 要素)    events_after /             集約を replay で       ├──▶ 表の DAO ──▶ 表 B
             events_through             起こし、クエリの        └──▶ チェックポイントの DAO
                │                       答えを写す                    ──▶ 処理したシーケンス番号
                │                                                           │
                └── BEGIN IMMEDIATE ………（同じ DB トランザクション）……… COMMIT ──┘
 ファイルの DAO（1 ファイル = 1 表）は DB トランザクションに入れない（原則 6）
```

投影は取得の都合（接続・位置・DAO）を知らない（[cqrs-boundaries.md](cqrs-boundaries.md) 規則 3 の二層）。
判断は集約の側にあり、投影は集約を `replay` で起こしてクエリの答えを行へ写すだけである。

### 2. ポートは構造上の 1 要素の代理

ポートは、上の構造の**要素ごとに 1 本**立てる。`JournalReader` はジャーナルという要素の代理であり、
「ある位置より後／までの事実を読む」だけを持つ。**リードモデル側の型（行・表・チェックポイント）に依存しない**。

旧来の `JournalReader` は、ジャーナルを読む口と、リードモデルへ書く口（`publish` / `advance_checkpoint` /
`replace_*`）を 1 本に抱えていた（Issue #153）。書く口は、原則 3 の表の DAO へ移す。

**ジャーナルを読む口は `JournalReader` 1 本**（オーナー裁定 2026-09-26）。ジャーナルは構造上 1 つの要素なので、
代理も 1 つである。更新器ごとに読みたい事実の種類が違うなら、読取の引数で絞る。移行中に置いた面ごとの
`…JournalReader`（`PlanApprovalJournalReader`・`WorkspaceDoctorJournalReader`）は暫定であり、移行の最後に消す。

### 3. DAO は単一テーブルの I/O だけ

DAO が扱うのは**単一テーブルの I/O だけ**である（オーナー「DAO はテーブル単一の I/O しかできないのです！」）。
DAO の責務は**リードデータの読み書きだけ**であり、判断・導出・順序の決定を持たない（オーナー「DAO はリードデータの
読み書きの責務だけになります」）。
**ファイルもリードモデルであり、1 ファイル = 1 テーブルとみなす**（ファイル 1 つにつき DAO 1 本）。

表をまたぐ検査・導出は DAO に置かない。置き場所は更新器（どの表をどの順に書くか、どの位置まで進めるか）か、
ドメイン／値の型（何が正しい行か）である。表の DDL（`CREATE TABLE IF NOT EXISTS` と索引）は、その表の DAO が持つ。

### 4. 命名と配置

- RMU 側の DAO も「**表名（ファイル名）＋ `Dao`**」／ 実装は「**…`DaoImpl`**」。表名の名前空間の接頭辞 `read_` は
  名前に含めない（クエリ側と同じ綴り — 例: `read_doctor_report` → `DoctorReportDao`）。
- trait は RMU クレートの `orchestration/port/`（クエリ側の `port/` と同型 — trait と、それが運ぶ値（行・読取レコード）が
  同居する）。実装は RMU クレート内（`orchestration/…_dao_impl.rs`）。
- クエリ側に同じ名前の DAO（`DoctorReportDao` など）があっても衝突しない。クエリ側クレートは RMU を `[dependencies]` に
  持てないので、RMU の DAO はクエリ側へ漏れない（[cqrs-boundaries.md](cqrs-boundaries.md) の判定表）。
- RMU 側の DAO は**書く DAO** である。クエリ側 DAO の「`find` のみ」（[gateway-taxonomy.md](gateway-taxonomy.md) §3）は
  クエリ側の規則であって、RMU 側には当たらない。

### 5. チェックポイント — 処理したシーケンス番号はリードモデル側の状態

更新器は、**保存したシーケンス番号より後のイベントを読み、DAO で更新し、処理したシーケンス番号を保存する**。
再起動時はその番号の次から始める。処理したシーケンス番号は**リードモデル側の状態**であり、その保存も DAO
（チェックポイントの表の DAO）が行う。

**なぜリードモデル側か**: 番号は「リードモデルがどの事実まで反映しているか」を述べる値であり、ジャーナル（事実）の
性質ではない。リードモデルを捨てて作り直すなら、番号も一緒に捨てて 0 から読み直すのが正しい。番号をジャーナル側に
置くと、リードモデルと番号が別々の理由で動き、「行は古いのに番号だけ進んだ」（読取コマンドが永久に古い答えを見る）か
「行は新しいのに番号が古い」（同じ事実を二度書く）のどちらかが起こりうる。

番号は**ジャーナル上の位置**（全集約横断の通番 — SQLite 実装では `journal` の `rowid`）であり、集約内の通番
（`seq_nr`）ではない。集約内の通番は集約ごとに 1 から始まるので、「どこまで読んだか」を表せない。

### 6. トランザクション

- 1 つのイベント（またはバッチ）で複数の表を更新するときは、**処理したシーケンス番号の表も含めて 1 つの DB
  トランザクションで確定してよい**。開き方は **IMMEDIATE**（#134 の教訓 — 読んでから書くトランザクションを
  DEFERRED で始めると、別の書き手がいるときの書込昇格が busy timeout を待たずに即 `SQLITE_BUSY` になる）。
- **ファイルと表をまたぐトランザクションは使えない**。ファイルはロールバックされないので、ファイルの DAO は
  トランザクションに入れない。「トランザクションの中でファイルを書いてからコミットする」形は、コミットに失敗すると
  ファイルだけが進んだ状態を残す。原子的に見えるだけで、原子性は成り立っていない。
- **追記するファイル**（監査シャードなど）は、ファイルごとに「どのシーケンス番号まで反映したか」を持ち、その番号以下の
  イベントは書かない（冪等）。これで「ファイルへ追記した後、表のコミットの前に落ちた」ときも、再実行が同じブロックを
  二重に追記しない。
- **丸ごと置き換えるファイル**は、再実行しても同じ結果になる（同じ事実からは同じ内容が出る）ので、番号を持たなくてよい。

## 実装の形

### トランザクションの受け渡し（オーナー裁定 2026-09-26 — PR1 で採った形を全更新器の形として承認）

DB トランザクションの受け渡しは次の形にそろえる。PR1（自己診断の更新器）で採った形を、オーナーが全更新器の形として
承認した。

- **更新器が接続を 1 本所有し、`BEGIN IMMEDIATE` でトランザクションを開く**。確定（`commit`）と取り消しは更新器が決める。
  途中で失敗したらトランザクションは確定されずに捨てられ、どの表も番号も動かない。
- **表の DAO は接続を持たない**（状態の無い値）。書込メソッドはトランザクションを **`&mut rusqlite::Transaction<'_>`** で
  受け取る。`&mut` にするのは、書込であることをシグニチャで示すためである（DAO 自身は変わらないので `&self`。可変性を
  内部に隠していない — [interior-mutability.md](interior-mutability.md)）。
- **読取は `&rusqlite::Connection`** で受け取る（トランザクションは参照外しで渡せる）。チェックポイントの読取と
  ジャーナルの読取は、書込ロックを取った同じトランザクションの上で行う — 読んだ位置と書き戻す位置が食い違わない。
- **スタティックディスパッチ**。更新器はジャーナルの読み手と表ごとの DAO を型引数で持つ
  （`WorkspaceDoctorReadModelUpdater<J, R, C, K>`）。実物の組は `open` が作る。
- ポート面に `rusqlite` の型が現れる。これは RMU クレートの内側の話であり、SQLite への依存は RMU の本質的な結合で
  ある（[cqrs-boundaries.md](cqrs-boundaries.md) の判定表 — 2026-08-29 裁定）。クエリ側ポートの「媒体を契約に
  漏らさない」とは射程が違う。
- ジャーナルの読み手は、移行中だけ面ごとに `…JournalReader`（例: `WorkspaceDoctorJournalReader`）として立てる。
  旧 `JournalReader` はまだリードモデルへの書込を抱えているので、それを流用すると書く口ごと依存してしまうため
  である。移行の最後に `JournalReader` 1 本へまとめて消す（原則 2 — オーナー裁定 2026-09-26）。

## 判定

```text
この更新器・ポートは正しい形か？
├─ ポートがジャーナルを読む以外のこと（行・表・番号の書込）をする ── ✕ 原則 2
├─ 1 つの DAO が 2 つ以上の表（またはファイル）に触れる ─────────── ✕ 原則 3
├─ DAO が表をまたぐ検査・導出をする ─────────────────────────── ✕ 原則 3（更新器かドメインへ）
├─ 処理したシーケンス番号を DAO 以外（更新器の生 SQL・ジャーナル側）が書く ── ✕ 原則 5
├─ 複数の表と番号を別々のトランザクションで確定する ──────────────── ✕ 原則 6
├─ 読んでから書くトランザクションを DEFERRED で開く ──────────────── ✕ 原則 6（#134）
├─ ファイルの書込を DB トランザクションの中に入れて原子的だと見なす ───── ✕ 原則 6
├─ 追記ファイルが「どの番号まで反映したか」を持たない ─────────────── ✕ 原則 6
└─ どれにも当たらない ──────────────────────────────────── ○
```

## 禁止パターン

- `ReadModelWriter` のような、複数の表・ファイルへ書く大きなポートを作る（原則 1）
- `JournalReader` にリードモデルへの書込（`publish` / `advance_checkpoint` / `replace_*` の類）を足す（原則 2）
- DAO の中で別の表を読んで判断する、または 2 つの表へ書く（原則 3）
- 更新器が DAO を通さずに生の SQL やファイル I/O でリードモデルを書く（原則 1・3）
- 処理したシーケンス番号として集約内の通番（`seq_nr`）を保存する（原則 5）
- 全履歴を毎回読み直して全行を差し替える形を、番号を持たずに「冪等だから」で済ませる — 再起動時に「その番号の次から
  始める」ができない（原則 5）
- ファイルを書いてから表をコミットする形で、ファイルと表の原子性を前提にする（原則 6）

## 射程／対象外

- **射程**: `modules/core/read-model-updater`（RMU）の更新器と、そのポート・実装。
- **移行中である**。2026-09-26 時点でこの形に移したのは自己診断（`WorkspaceDoctorReadModelUpdater`）だけで、
  ほかの更新器（取得ループ本体・構造化面・テスト契約・計画指紋・Code Generation 開始可否・runtime-graph・停止制御・
  心拍・承認ランタイム）は旧来の形のまま残っている。移行の順序は
  [rmu-dao-migration-plan-20260926.md](../../rmu-dao-migration-plan-20260926.md)。移行が済むまで、既存の更新器を
  この規則で「違反」として止めない（新規に書く更新器と、手を入れる更新器には適用する）。
- **対象外**: コマンド側の Repository（[gateway-taxonomy.md](gateway-taxonomy.md) §1・§2）と、クエリ側の DAO
  （同 §3。読取だけ・`find` のみ）。
- **対象外**: 参照入力（memory 層の規則ファイルなど、人が編集するファイル）の**読取**。これはジャーナルではないので
  `JournalReader` の要素ではない。読み手は取得ループが持つ（[cqrs-boundaries.md](cqrs-boundaries.md) 規則 3）。

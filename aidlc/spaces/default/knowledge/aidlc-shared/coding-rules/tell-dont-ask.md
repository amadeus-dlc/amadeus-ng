# Tell, Don't Ask — 業務判断をドメインへ委譲し、I/OのID受け渡しを区別する

**裁定日**: 2026-08-22（オーナー）
**出典**: オーナー自作スキル [j5ik2o-tell-dont-ask](https://github.com/j5ik2o/ai-tools/tree/main/plugins/software-design/skills/j5ik2o-tell-dont-ask) / [j5ik2o-breach-encapsulation-naming](https://github.com/j5ik2o/ai-tools/tree/main/plugins/software-design/skills/j5ik2o-breach-encapsulation-naming)
**適用例**: PR #12（reap 適格判定のドメイン抽出（退役済み — ADR-007 / Bolt B5。以後は履歴としての例）・CheckboxState 分類述語）
**機械強制**: `cargo lint`（`checkbox-vocabulary` / `use-case-domain-getter`。ルール追加時は検出力を証明する赤例テスト必須）

## ユースケースでの禁止とI/Oの例外（2026-09-14 オーナー裁定）

ユースケースは、ドメインの状態をgetterで取り出して、その所有者が担う業務判断を組み立ててはならない。状態の所有者へ判断や状態遷移を依頼する。

**I/Oの対象を指定するため、型付きIDをRepositoryの `find_by_id` に直接渡すgetterは許可する。** 2026-09-05の「IDの受け渡しも含む一律禁止」を、この用途に限って改訂した。参照先IDを読むためだけに、Repositoryが参照元の集約や値オブジェクト全体を引数に取る形は使用しない。

```rust
let intent = self.intents.find_by_id(execution.intent_id()).await?;
let definition = self.definitions.find_by_id(intent.definition_id()).await?;
let policy = intent.resolve_review_policy(&definition, stage)?;
```

許可範囲は次のとおり。

- Repositoryポートの `find_by_id` が受け取る型と一致する、ドメインの `XxxId` を直接渡す。借用・括弧・IDの `clone()`、UFCS（型名を明記したメソッド呼出し）も同じ扱いとする。
- IDを比較・分岐・変換して業務判断を作ること、`as_str()` 等で内部表現を取り出すこと、ID以外の状態を読むことは許可しない。
- 検査範囲を明確にするため、ID取得をローカル変数・補助関数・ブロックへ移す形も許可しない。Repository呼出しの引数に書くだけで、引数内部の任意の処理が許されるわけではない。
- ドメインオブジェクトを経由するgetterの連鎖全体を許可しない。許可するのは最後の型付きIDの取得だけである。

インターフェイスアダプタ層でのgetter呼出しは合法である。永続化・外部表現への変換・描画など、
境界の処理がデータを読むことまで禁止しない。ドメインにgetterを定義すること自体も禁止しない。

分類・可否・次の動作を答えるドメインの述語や判断メソッド、状態を遷移させるコマンドはgetterではない。
ただし、`is_`等へ改名しただけの生のbooleanフィールド取得はgetterである。
ユースケース所有の入力型・クエリ側のView・標準型のメソッドは、このドメインgetter禁止の対象ではない。
テストの状態検証は従来どおり対象外とする。

`cargo lint`の `use-case-domain-getter` が、ドメイン型の定義と呼出先を照合して検出する。
単なるメソッド名のブラックリストではなく、ドメインの保持データを返すメソッドが対象になる。I/Oの例外も、コマンド側のRepository traitの宣言・検索メソッドの引数型・getterの戻り値型を照合する。通常型の同名メソッドや型が一致しない引数は例外にしない。
検出範囲の詳細と構文解析の限界は `tools/lint` の実装・テストに記録する。

**実装途中にも検査する（2026-09-08利用者指示）**: まとまった実装・リファクタリング・是正の区切りで `cargo lint` を実行し、検出した違反をその都度直す。最終工程だけに検査を残さず、`cargo fmt` やClippyの成功で代用しない。getterの改名、補助関数やラッパーへの移動、検査の抑止を是正とは扱わない。機械検査で捉えきれない判断の流出は、コードレビューでも確認する。

是正例（2026-09-05）: `CommitVerdictUseCase` は入力getterを読み直して遷移を組み立てず、
`ReportRequest::for_retry_at` と `IntentExecution::apply_report` に任せる。
`Intent::resolve_review_policy` が依頼のスコープと指定を使ってレビュー方針を判断し、
`record_single_stage_run` がステージ名から実行対象を解決する。添字を取る旧署名や別名は残さず、呼出側も一斉に改める。
ユースケースは判断結果や拒否の文脈を受け取り、保存と再試行を進行管理する。
関連取得は、ユースケースが参照先IDを `find_by_id` に渡して依頼する。Repositoryは自分の集約の再構成と保存を担い、業務判断はドメインに残す。

## 適用領域（2026-08-22 オーナー明確化）

以下はドメイン内の判断とI/O境界に関する一般則である。ユースケースには上の2026-09-14裁定を適用し、Repositoryへの型付きIDの直接受け渡しだけをgetter禁止の例外とする。
リポジトリ・Gatewayの永続化、JSON等への変換、Presenterの描画でデータを読むことは合法である。

## ルール

- **違反** = 他オブジェクトから getter で状態を抜き出し、**その所有者が持つべき（または既に持つ）判断**を呼出側で実装すること。典型形: `if b.x() == .. && b.y() > .. { /* A が B の代わりに決める */ }`。
- 判断は状態の所有者へ移す。値の分類語彙（例: `CheckboxState` の in-flight / finished / active）はその型が述語として公開し、呼出側は変種集合を再列挙しない。
- ドメインに判断の単一実装があるとき（例: `CheckboxState` の分類述語 in-flight / finished / active）、呼出側は生データから同じ判断を再実装せず委譲する。境界規約（`>` か `>=` か等）や変種集合を 2 箇所に重複させない。
  - 履歴上の実例だった `lock_protocol::reap_eligible`（Gateway が `stale_ms` 比較を再実装しないよう境界規約を単一実装に閉じ込めた例）は退役済み — ADR-007 / Bolt B5。以後は履歴としての例であり、規範は上の `checkbox-vocabulary` の例で成立する。

## 違反に数えない（明示的例外）

- テストコードのアサーションとテストドライバ（ITF 準拠の状態射影突き合わせを含む）
- Presenter / 描画 / エラーメッセージ組み立てのためのデータ射影
- 境界での写像（serde ワイヤ構造体 → ドメイン型の parse-don't-validate）
- 意図的な読取モデル / Published Language のクエリ（`WorkflowDefinition` の 5 述語、`ScopeGrid` の 3 値照会 = B1 裁定）。ただし読取モデルが述語として公開済みの判断を生アクセサから再実装するのは違反
- 値オブジェクトの述語クエリ（`mode.is_autonomous()` 等）を訊いて**呼出側自身に帰属する判断**を下すもの
- 集約ルートが自分の境界内の子・自フィールドを読むもの
- I/O Gateway がファイルシステム状態を見て I/O を組み立てるもの（ドメインに同じ判断の関数がある場合を除く）

## 不可避な公開の命名

永続化・シリアライズ・テスト・framework glue のためにどうしても内部状態を晒すアクセサは `breach_encapsulation_of_x` と命名し、侵害を可視化する（この命名方式の採否は導入時にオーナー確認）。
ユースケースでの呼出禁止と上記のI/O例外は、この命名方式の採用を待たずに適用する。

## 集約所有の前提集合

ゲート前提（I7）や skipped 受理前提（I13）のような**集約が所有する遷移前提の変種集合**は分類語彙の再実装ではない。lint には `// amadeus-lint: allow(<rule>) — 理由` で明示し、理由に不変条件番号を書く。

## 追記 2026-08-24（オーナー指摘）— アクセサで内部型を意識させない

**newtype / 値オブジェクトのアクセサを `value()` / `inner()` / `raw()` と名乗ってはいけない。**
理由は名前が短いからでも型名が入っていないからでもなく、**その名前が「私は何かを包んだ箱で、
これが中身です」と言っている**からである。呼び手はその型を概念ではなく容器として扱いはじめ、
内部表現が公開面に漏れる。

実例（2026-08-24 是正）: `StageIndex::value() -> usize` は、`StageIndex` を「usize が入った箱」
として意識させていた。`to_usize()` へ改めたのは**型名を名前に入れるためではなく**、
「中身を出す」ではなく「境界を越えて `usize` へ変換する」と言い直すためである。

### 何に置き換えるかは場面による

「行き先の型を名前に出す」は**この場面での解**であって規則ではない。まず問うのは
**そもそもその値を外に出す必要があるか**である。

1. **出さなくて済まないか** — 呼び手が中身を取り出して自分で判断しているなら、その判断を
   型の側へ移す（本ルールの本体）。アクセサ自体が消えるのが最良
2. **ドメインの意味を持つクエリにできないか** — `is_final()` / `follows(other)` のように、
   呼び手が本当に知りたいことを型が答える
3. **境界を越える変換なら、変換として名乗る** — `as_str()` / `to_usize()` / `to_u64()`。
   C-CONV に従う（`as_` = 借用、`to_` = 所有/コピー、`into_` = 消費）

3 に落ちるのは、**プリミティブへ降りることが本当に必要な境界**（索引計算・ワイヤ表現・
外部 API）だけである。1 や 2 で済むものを 3 で解決すると、名前が整うだけで漏洩は残る。

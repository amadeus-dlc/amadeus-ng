# 集約は他の集約・エンティティを ID で参照する — オブジェクトの埋め込み禁止

**裁定日**: 2026-08-29（オーナー。B12 設計中に `IntentExecution` が `intent: Intent` を
埋め込む誤設計をオーナーが検出・却下したことによる明文化 — 「集約を理解してないだろ」）
**土台**: 集約 = 整合性境界（トランザクションの単位）。[cqrs-boundaries.md](cqrs-boundaries.md)
（コマンド側の最新状態は常に集約から）、[abstract-data-type.md](abstract-data-type.md)
**適用例**: B12 — `IntentExecution { intent_id: IntentId, .. }`（`intent: Intent` の埋め込みは却下）
**機械強制**: レビュー基準（`cargo lint` ルール候補: 集約 struct のフィールド型に他の
集約・エンティティ型が現れたら違反 — 赤例テスト必須）

## 原則

**集約が他の集約・エンティティを参照するときは、その識別子（`XxxId`）だけを保持する。
オブジェクトそのものをフィールドに埋め込んではならない。**

```rust
// ✕ 埋め込み — 整合性境界が曖昧になり、1:n なら n 個の複製を抱える
pub struct IntentExecution { intent: Intent, /* … */ }

// ○ ID 参照
pub struct IntentExecution { intent_id: IntentId, /* … */ }
```

## なぜか

1. **整合性境界が壊れる。** 集約はトランザクションの単位である。他エンティティを埋め込むと、
   その複製がこの集約のイベント・スナップショットに焼き込まれ、「どちらが正か」という
   問いが生まれる（正はエンティティの所有者側にしかない）。
2. **多重度に耐えない。** 参照先と 1:n の関係（例: 1 Intent : n IntentExecution）では、
   埋め込みは n 個の複製を意味する。
3. **集約が痩せる。** 保持するのは自分が所有し遷移させる状態だけになり、スナップショットも
   縮む。

## 参照先のデータが判断に必要なとき — パラメータで渡す

埋め込みの動機は「コマンド・クエリの判断に参照先のデータが要る」ことだが、その解は
**メソッド引数で `&` 参照を渡す**ことである（本リポジトリの既存の家風 —
`next_decision(&self, &WorkflowDefinition, ...)` / I8 の「Controller が読んで `&` で渡す」）。

```rust
// 計画が要る判断は &Intent を引数で受ける。保持はしない
pub fn approve_gate(&mut self, intent: &Intent, ...) -> Result<IntentExecutionEvent, E>
```

- 受け取り側は**取り違えをガードする**: `intent.id() == self.intent_id` を検査し、
  不一致は `Err` で拒否する（ID 参照だからこそ照合が書ける）。
- 読み込んで渡すのは Controller / 合成ルートの仕事。ユースケース・集約は取得手段を持たない。

## イベントに材料の複製が載るのは違反ではない

`Started` が intent の材料を丸ごと運ぶのは本規則の違反では**ない**。イベントは「その時点の
事実の自己完結な記録」であり（投影核の入力はイベントだけ —
[cqrs-boundaries.md](cqrs-boundaries.md) 規則 3）、複製ではなく**歴史**である。禁止されるのは
**集約の保持状態**（スナップショットに載る形）への埋め込みであり、`apply` は
イベントから自分が所有する分（ID と実行時状態）だけを取り込む。

## 禁止パターン

- 集約 struct のフィールドに他の集約・エンティティ型（`Intent`・`WorkflowDefinition` 等）が現れる
- 「便利だから」参照先のオブジェクトをスナップショットに焼き込む
- 埋め込みを避ける目的で、参照先の**フィールドをバラして**大量に複製保持する（同罪 —
  B12 以前の旧 `WorkflowExecution` が `stages`・`scope`・`request` を保持していた形。
  判断に要るならパラメータで渡す）

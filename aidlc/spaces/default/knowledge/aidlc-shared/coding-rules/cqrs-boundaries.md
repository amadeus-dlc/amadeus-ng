## 原則

本プロジェクトは CQRS + イベントソーシングを採用している。書込モデルは集約
`IntentExecution`（~~`WorkflowExecution`~~ 分割・改名 2026-08-29 — 静的な intent は不変構造体 `Intent` へ）と `EventStore`（ジャーナル + スナップショット）、読取モデルは
`aidlc-state.md` と監査シャードで、`ReadModelUpdater`（RMU）が投影して更新する。

依存の規則は 4 つ（オーナー明言 2026-08-24）。

1. **コマンド側はクエリ側に依存しない。**
2. **クエリ側はコマンド側に依存しない。**
3. **投影核が要るのはドメインイベントだけ。** RMU は二層でできている（2026-08-28 改訂）:
   **取得ループ**（`JournalReader` で差分を引き、チェックポイントを進める — RMU 自身の仕事）と、
   **純粋投影核** `project(events, read_model)`（ドメインイベントだけを受け取り、リードモデルを
   作成・更新する）。「イベントだけ」の制約は投影核に掛かる。SQLite にはストリームが無いので、
   AWS 版 RMU が Streams から**受信する**のと同じ役割を、ここでは**自分で引く**形で果たす。
4. **コマンド側は最新状態を常に集約から判断する。**

追加の規則 3 つ（オーナー明言 2026-08-30 — 逐語に近い形で記録する。**この説明を
二度とさせないこと**）。

5. **コマンド側のユースケースは最終的に書き込む。** その書き込みのためなら、集約の
   最新状態を読む（リポジトリで再構成する）ことは許容される。**が、ただ集約や集約以外の
   データを読むための責務はコマンド側では許容されない** — それはクエリ側の実装
   （`core/query/interface-adapter`・`core/query/use-case`）である。
   帰結: `next` / `continue` のような**読むだけ**（directive を出すが何も書かない）の
   ユースケースはクエリ側ユースケースであり、コマンド側に置くのは違反。コマンド側に残る
   ユースケースは書き込むもの（例: `CommitVerdict`）だけである。
6. **クエリ側は RMU が構築したリードモデルだけに依存する。** リードモデルはリード DB 上や
   ファイルシステム上にある（`aidlc-state.md`・監査シャード・`stage-graph.json` …）。
   クエリ側はドメインに絶対依存せず、**集約の再構成もしない** — リードモデルを自分の
   クエリモデルへ写して読むだけである。
7. **`stage-graph.json` の来歴**: コマンド側の集約（compile コンテキスト）から発生した
   イベントを RMU が捉えて作成・更新するリードモデルであり、**クエリサイドはこれを読む
   だけ**である。コマンド側がこれを読む・パースする実装を持つのは違反（2026-08-30 に
   実際に起きた誤り — `workflow_definition_parse.rs` をコマンド側アダプタに置いた）。

**steering の配信計画はドメインモデルではない**（オーナー裁定 2026-08-31、b26 段階2 — 規則 7 と
同じ理屈の具体形）: `SteeringPlan`（ステージへ配る規則束の配信計画）は**リードモデル由来の
クエリ側の配信計画モデル**であり、ID を持つ集約ではない。したがってコマンド側 domain から
撤去し、`RuleBundleSource` ポートも退役させた。読むだけの材料は、クエリ側が自分のクエリモデル
として持つ。

**分類の自己検査**（アンカリング防止）: 新しい責務を置くとき・既存の責務を動かすときの
最初の問いは「**これは読むのか、書くのか**」である。書かないならクエリ側。既存コードが
どこに居るか・過去の Bolt で何が承認されたかは分類の根拠にならない — 原則が常に勝つ。

**リポジトリの使い方**（オーナー裁定 2026-08-30 追補 — 規則 5 の具体形）:

- リポジトリは **`find_by_id` と `store` の両方**を持つ。正しい使い方は 1 つだけ —
  **`find_by_id` で集約を取得 → ビジネスロジックを実行 → 更新された集約を `store` で保存**。
- **`find_by_id` だけを呼んで何も書かないユースケースは違反**である。それは「読むだけ」で
  あり、クエリ側（リードモデルを読む実装）の仕事である。読取専用ポートの注入で
  「書けない」を型保証する旧手法（use-case-rules §2b/§4 の I8 型）は、読むだけの
  ユースケース自体がコマンド側に存在しなくなるため前提ごと失効する。
- **`WorkflowDefinitionRepository` はコマンド側に残る通常のリポジトリ**である —
  `WorkflowDefinition` を `find_by_id` も `store` もできる（`store` の実装は定義を変更する
  最初のユースケースと同じ Bolt で書く — 先行実装しない）。intent 新規作成ユースケース
  （新しい仕事の開始依頼から `Intent` 集約を作成・保存する書込）は「定義を `find_by_id` →
  `Intent::create` → 新生集約を `store`」であり、この型に収まる。規則 7 が禁じるのは
  **読むだけの責務**（next/continue 等）がコマンド側で stage-graph.json を読むことであり、
  書込ユースケースの中の集約再構成（規則 5）はこの限りではない。

```text
コマンド側 (core-command-domain / -use-case / -interface-adapter)
  = 書くためだけの世界（集約を読むのは書くための再構成のみ）
        │
        │ ドメインイベント
        ▼
  RMU (core-read-model-updater) — 中間。イベントを捉えてリードモデルを作成・更新する
        │
        │ リードモデル (aidlc-state.md / 監査シャード / stage-graph.json — リード DB /
        │               ファイルシステム上)
        ▼
クエリ側 (core/query/interface-adapter, core/query/use-case)
  = RMU が構築したリードモデル**だけ**に依存して読む。
    ドメインへの依存は絶対禁止・集約の再構成もしない。独自のクエリモデルを持つ。
```

**RMU はコマンド側でもクエリ側でもない — 中間**である（オーナー裁定 2026-08-29。2026-08-24
原裁定「RMU はコマンドサイドとクエリサイドに依存できる」がそのまま生きる）。RMU はコマンド側の
**ドメインイベントに依存でき**、クエリ側（リードモデル）にも依存できる。**ドメイン
（`core-command-domain`）はコマンド側の持ち物**であり、**クエリ側のクレートはドメインに
絶対依存しない**。両側を知ってよいのは **RMU と合成ルート（U7）だけ**である。

投影核の入口はドメインイベント 1 本に絞る:

```rust
// 純粋投影核 — イベントだけを受け取る。JournalReader・接続・チェックポイントを知らない
fn project(events: &[IntentExecutionEvent], read_model: &mut ReadModel) -> Result<(), E>

// RMU コンポーネント — 取得ループは RMU 自身が持つ（2026-08-28 裁定）。形の要点のみ:
//   checkpoint 読取 → events_after で差分取得 → project → advance_checkpoint
```

イベントを運ぶのは **RMU 自身**である（2026-08-28 改訂 — 従来の「合成ルートが読んで渡す」は
失効）。合成ルート（U7）は RMU を**起動するだけ**で、駆動ループを持たない — 合成ルートは
カバレッジ除外領域（インタビュー Q5 裁定）であり、ループの実ロジック（バッチ・チェック
ポイント単調性・エラー処理）をテストの届かない場所に置かないため。投影核は `JournalReader` を
一切知らずに単体テストでき、取得ループは RMU クレート内でテストされる。

## なぜ 4 が「禁止」ではなく「不可能」なのか

コマンド側がリードモデルを読んで現在状態を得るのは、規約違反である以前に**物理的にできない**。
**リードモデルは常に遅延している**からである。投影はチェックポイント以降のイベントを後から
適用するので、いま書き込もうとしているコマンドが見るべき最新状態がそこに載っている保証はない。

したがってコマンド側の現在状態は、**必ず集約から**得る — スナップショット + ジャーナル replay
（`find_by_id` による再水和）である。リードモデルを覗きに行く設計は、遅延の分だけ静かに壊れる。

## 機械強制 — クレート境界

依存規則は**クレートを分けて `Cargo.toml` に相手を書かない**ことで強制する。本プロジェクトが
層の依存強制に採っている機構がこれであり（team.md「依存は Cargo.toml の不在により物理的に
内向き強制」）、CQRS 境界にだけ適用しない理由はない。

**モジュール分割（同一クレート内の `mod`）では強制にならない。** `pub(crate)` で相互参照できて
しまうので、規律だけが頼りになる。

配置（ADR-009）:

| クレート | 側 | `Cargo.toml` に書いてよい相手 |
| --- | --- | --- |
| `core-command-domain` | **コマンド** | 共有層のみ**許可**（言語拡張 `core-infrastructure` は使ってよい — 義務ではない。現時点の実依存は外部ライブラリのみ）。**ドメインはコマンド側の持ち物**（2026-08-29 オーナー裁定） |
| `core-command-use-case` | **コマンド** | `core-command-domain`。クエリ側と RMU は禁止 |
| `core-command-interface-adapter` | **コマンド実装** | コマンド側 + 本家ストア。クエリ側と RMU は禁止 |
| **`core-read-model-updater`（RMU）** | **中間** — どちらの側でもない | **コマンド側のドメインイベントにもクエリ側にも依存できる**（2026-08-24 原裁定）。共有層 + rusqlite も可。`JournalReader` ポートも SQLite 実装も RMU 自身が所有 |
| クエリ側クレート（将来のリードモデル読取・クエリ API 層） | **クエリ** | 共有層のみ。**ドメイン（`core-command-domain`）は絶対禁止**（2026-08-29 オーナー裁定）。コマンド側・RMU も禁止 |
| 共有層 | — | `core-infrastructure`（言語拡張 — どの層も知らない）のみ（2026-08-29 shared 解体 — 監査・directive 語彙は `core-command-domain` へ、canon-json は infrastructure へ、文言は出す側へ。**ドメインの pub 型がそのまま公開言語**なので独立の語彙クレートは不要） |

読取側の契約（`JournalReader` / `ProjectionName` / `GlobalSeqNr`）を中立クレートへ
切り出す必要は**ない** — 呼ぶのは RMU だけなので、**RMU クレート自身が所有する**
（2026-08-28 裁定）。**SQLite 実装（`JournalReaderImpl`）も RMU クレートに置く**
（2026-08-29 オーナー裁定 — ジャーナルを読むことが RMU の仕事そのものであり、
ストレージ依存は RMU の本質的結合）。コマンド側とクエリ側の間の共有部品は側の独立を DRY に
優先して扱う（エラー分類・I/O 写像は側ごとに専用化）。`StorePath` とイベントの直列化型判別子
（manifest 定数）は `core-command-domain` にあり、**中間である RMU はそれに依存してよい**
（2026-08-29 是正 — RMU はコマンド側のドメインイベント・語彙に依存できる）。

**判定は `Cargo.toml` を見るだけでよい。** コマンド側クレートの依存にクエリ側・RMU が現れたら
違反。クエリ側クレートの依存にコマンド側（**ドメイン `core-command-domain` を含む — 絶対禁止**）
・RMU が現れたら違反。**RMU はどちらが現れてもよい**（2026-08-24 原裁定 — 中間である RMU だけの
特権）。判定の「相手」は側のクレートであり、共有層（`core-infrastructure` / shared の
のみ）と外部ライブラリは対象外。

## 禁止パターン

- コマンド側のユースケースがリードモデル（状態ファイル・監査シャード）を読んで判断する
- **コマンド側クレートの `Cargo.toml` にクエリ側クレートが現れる**
- **クエリ側クレートの `Cargo.toml` にコマンド側クレートが現れる**
- コマンド側・クエリ側が RMU を `Cargo.toml` に書く（依存は RMU → 両側の一方向）
- **クエリ側クレートがドメイン（`core-command-domain`）を `Cargo.toml` に書く**（絶対禁止 —
  2026-08-29 オーナー裁定）
- 同一クレート内の `mod` 分割で CQRS 境界を表現したつもりになる
- コマンド側が「速いから」リードモデルをキャッシュとして読む（遅延の分だけ静かに壊れる）
- 「両側を知ってよい」を合成ルート（app）以外へ持ち込む
  （両側を知ってよいのは RMU と合成ルートだけ）
- **純粋投影核が取得の都合を知る** — `project` のシグネチャに `JournalReader`・SQLite 接続・
  チェックポイントが現れる（取得ループと投影核の二層を潰してはいけない）
- **駆動ループを合成ルート（U7）に置く** — カバレッジ除外領域に実ロジックが落ちる。
  U7 が持ってよいのは RMU の起動だけ（2026-08-28 裁定）
- 投影核がイベント以外のコマンド側の型（集約・Repository・ストアのエラー）を入口に取る

## 対象外

- ~~アダプタ層は両側の契約を実装してよい~~ — **失効（2026-08-29 オーナー裁定）**:
  use-case も interface-adapter も**側で分割する**（`core-command-*` / RMU）。1 つの
  クレートがコマンド側とクエリ側の実装を同居させてはならない。両側を知ってよいのは
  合成ルート（U7）だけである。
- **合成ルート**（`main.rs` / U7）は両側を知る。それが合成ルートの仕事である。

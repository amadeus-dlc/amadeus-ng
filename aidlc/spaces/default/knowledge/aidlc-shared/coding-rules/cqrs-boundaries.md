# CQRS の依存境界 — クエリ側とコマンド側は相互に独立

**裁定日**: 2026-08-24（オーナー）
**関連**: ADR-001（ES 採用）/ ADR-003（互換ファイルはリードモデル + RMU）/ ADR-004（状態ファイルは
リードモデル）/ **ADR-009（本規則の記録）**、[gateway-taxonomy.md](gateway-taxonomy.md) §4
**機械強制**: **クレート分離**（`Cargo.toml` に相手が現れないこと）。違反はビルドで落ちる

## 原則

本プロジェクトは CQRS + イベントソーシングを採用している。書込モデルは集約
`WorkflowExecution` と `EventStore`（ジャーナル + スナップショット）、読取モデルは
`aidlc-state.md` と監査シャードで、`ReadModelUpdater`（RMU）が投影して更新する。

依存の規則は 4 つ（オーナー明言 2026-08-24）。

1. **コマンド側はクエリ側に依存しない。**
2. **クエリ側はコマンド側に依存しない。**
3. **RMU が要るのはドメインイベントだけ。** RMU はイベントを**受信して**リードモデルを
   作成・更新する。それ以外は要らない — ジャーナルを読みに行くのも、チェックポイントを
   進めるのも RMU の仕事ではない。RMU は両者の間に立つ第三の要素として、両側に依存してよい
   立場にはあるが、**実際に必要なのはイベント型とリードモデルの書込先だけ**である。
4. **コマンド側は最新状態を常に集約から判断する。**

```
コマンド側  ←── RMU ──→  クエリ側
    ↑                       ↑
    └──── 依存しない ───────┘
```

RMU だけが両側を知ってよい。だから RMU が「橋」であり、**両側は互いを知らないまま結合できる**。

ただし**橋であることと、両側を広く使ってよいことは別**である。RMU の入口はドメインイベント
1 本に絞る:

```rust
// RMU の形（受信する側であって、取りに行く側ではない）
fn project(events: &[WorkflowExecutionEvent], read_model: &mut ReadModel) -> Result<(), E>
```

イベントを**誰が運ぶか**は RMU の関心ではない。ジャーナルの読取とチェックポイントの前進は
**呼び出す側**（合成ルート）の仕事である。こうすると RMU は純粋な投影関数になり、
コマンド側のポート（`JournalReader` / `EventStore`）を一切知らずに単体テストできる。

## なぜ 4 が「禁止」ではなく「不可能」なのか

コマンド側がリードモデルを読んで現在状態を得るのは、規約違反である以前に**物理的にできない**。
**リードモデルは常に遅延している**からである。投影はチェックポイント以降のイベントを後から
適用するので、いま書き込もうとしているコマンドが見るべき最新状態がそこに載っている保証はない。

したがってコマンド側の現在状態は、**必ず集約から**得る — スナップショット + ジャーナル replay
（`find_by_id` による再水和）である。リードモデルを覗きに行く設計は、遅延の分だけ静かに壊れる。

## 機械強制 — クレート境界

依存規則は**クレートを分けて `Cargo.toml` に相手を書かない**ことで強制する。本プロジェクトが
層の依存強制に採っている機構がこれであり（team.md「依存は Cargo.toml の不在により物理的に
内向き強制」）、CQRS 境界にだけ適用しない理由はない。

**モジュール分割（同一クレート内の `mod`）では強制にならない。** `pub(crate)` で相互参照できて
しまうので、規律だけが頼りになる。

配置（ADR-009）:

| クレート | 側 | `Cargo.toml` に書いてよい相手 |
| --- | --- | --- |
| `core/domain` | 共有 | — |
| `core/use-case` | **コマンド** | `core/domain`。**クエリ側と RMU は禁止** |
| クエリ側クレート | **クエリ** | `core/domain`。**コマンド側と RMU は禁止** |
| **RMU クレート** | **橋** | `core/domain`（**ドメインイベント**）+ クエリ側。コマンド側の**ポート**（`JournalReader` / `EventStore`）は要らない — イベントは呼び出す側が運ぶ |
| `core/interface-adapter` | 実装 | `EventStoreImpl` が `EventStore` と `JournalReader` を実装 |

読取側の契約（`JournalReader` / `ProjectionName` / `GlobalSeqNr`）を中立クレートへ
切り出す必要は**ない**。RMU がそれらを使わないからである — コマンド側の `core/use-case` に
置いたまま、**合成ルートが**それを使ってイベントを読み、RMU に渡す。

**判定は `Cargo.toml` を見るだけでよい。** コマンド側クレートの依存にクエリ側が現れたら違反。
クエリ側クレートの依存にコマンド側が現れたら違反。RMU はどちらが現れてもよい。

## 禁止パターン

- コマンド側のユースケースがリードモデル（状態ファイル・監査シャード）を読んで判断する
- **コマンド側クレートの `Cargo.toml` にクエリ側クレートが現れる**
- **クエリ側クレートの `Cargo.toml` にコマンド側クレートが現れる**
- コマンド側・クエリ側が RMU クレートを `Cargo.toml` に書く（依存は RMU → 両側の一方向）
- 同一クレート内の `mod` 分割で CQRS 境界を表現したつもりになる
- コマンド側が「速いから」リードモデルをキャッシュとして読む（遅延の分だけ静かに壊れる）
- 「RMU が両側に依存してよい」を根拠に、**RMU 以外**のものへ両側依存を持ち込む
  （両側を知ってよいのは RMU と合成ルートだけ）
- **RMU がジャーナルを読みに行く**（`JournalReader` を注入する / 呼ぶ）。RMU は受信する側であり、
  取りに行く側ではない。イベントの供給とチェックポイントの前進は呼び出す側の仕事
- RMU がイベント以外のコマンド側の型（集約・Repository・ストアのエラー）を入口に取る

## 対象外

- **アダプタ層**は両契約を実装してよい（ADR-009）。SQLite スキーマ定義が 1 箇所に残るため。
- **合成ルート**（`main.rs` / U7）は両側を知る。それが合成ルートの仕事である。

# ドメインサービスは最後の手段 — まず所有する型の関連メソッドへ

**裁定日**: 2026-08-29（オーナー）
**関連**: [abstract-data-type.md](abstract-data-type.md)（土台 — 型は操作で定義される）、
[factory-naming.md](factory-naming.md)（構築規則は型が所有する）、
project.md Corrections「集約は FSM — 導出ロジックを独立ドメインサービスやユースケースに
置かない」（2026-08-22 横展開）の一般化
**機械強制**: レビュー基準

## 原則

**ドメインサービス（自由関数・独立サービス型）は消極的に使う。** 安易に作ると
オブジェクト指向らしさが失われる — 構築規則・導出・判断は、まずそれを所有すべき型の
関連メソッド／メソッドとして設計する。Rust でも新訳オブジェクト指向はできる
（オーナー明言 2026-08-29）。

判定は「**この操作を所有すべき型はどれか**」から始める。答えがある限り、その型の
`impl` に置く。自由関数として切り出してよいのは、**どの型も所有できない**ことを
説明できたときだけである（複数集約にまたがり、どちらの不変条件でもない操作など）。
その説明は doc コメントに書く — 書けないなら型へ戻す。

## 実例（是正）

`find_all_events(buffer) -> OrderedAuditEvents` は自由関数のドメインサービスとして
生まれたが、`OrderedAuditEvents` の doc 自身が「これを通ったものだけがこの型になる」と
述べていた — つまり**型の唯一の構築子**であり、所有者は明白だった。
`OrderedAuditEvents::find_in(buffer)` へ是正（2026-08-29。同型の先例:
`ResolvedPlan::find_in`）。仕様が「ドメインサービス（純関数）」と呼んでいても、それは
責務の所在（domain に残る）を言うだけで、自由関数という形を強制しない。

## 禁止パターン

- 型の唯一の（または主要な）構築経路を自由関数に置く — それはその型のファクトリである
- 「純関数だから」「仕様がサービスと呼んでいるから」を自由関数の理由にする
- 所有者を説明する doc コメント無しの自由関数ドメインサービス

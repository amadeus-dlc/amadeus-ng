# ドメイン同値関係は Eq/PartialEq で表現する

**裁定日**: 2026-08-22（オーナー）
**適用例**: `OwnerStamp`（等価 = upstream `stampMatches` の同一性。当初 PR #12 では `pid` + `startedAtMs` の 2 フィールドと推定したが、ピン留めソース採取で **`reapLiveOwnerAfterStale` も同一性の一部**と確定し 3 フィールド比較に修正済み — 同値関係の**中身**はドメイン/upstream の事実に従い、Eq で表現するという方針だけが不変）
**機械強制**: なし（レビュー基準）

## ルール

- 型に**ドメイン上の同値関係**が定義できるなら、名前付き比較メソッド（`names_same_holder` / `is_same_x_as` 等）を作らず、**`Eq`/`PartialEq` をその意味論で手実装**する（驚き最小化 — `==` がドメインの同値を意味する）。
- 同一性に含まれないフィールド（ポリシーフラグ・キャッシュ・将来の任意フィールド）は `eq` から除外し、**impl の doc コメントに根拠を明示**する。
- derive の構造的等価とドメイン同値が乖離する場合は**ドメイン側が勝つ**（derive をやめて手実装）。
- `Hash` を derive/実装する場合は `Eq` と整合させる（`a == b ⇒ hash(a) == hash(b)`）。

## 対象外

- **順序関数は同値関係ではない**。upstream の比較関数の写し（例: `StageNumber::numeric_cmp` = `numericStageOrder`。前置ゼロ違いを同値に扱う**順序**であり、`Ord`/`Eq` は生表現逐語保持の別関係）は upstream の関数名を保った名前付きメソッドのままでよい。
- エンティティの identity 比較で、値としての等価も別途意味を持つ場合は導入時にオーナー裁定（現時点で該当例なし）。

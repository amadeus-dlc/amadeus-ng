# 内部可変性は既定で禁止する — 可変操作はまず `&mut self` で設計する

**裁定日**: 2026-08-23（オーナー）
**参考**: [fraktor-rs `immutability-policy.md`](https://github.com/j5ik2o/fraktor-rs/blob/main/.agents/rules/rust/immutability-policy.md)（オーナー指示により本プロジェクト向けに翻案）
**適用例**: U3（Bolt B5）— `WorkflowExecutionRepository::store` が `&self` + `RefCell<EventStoreImpl<C>>`、`EventStoreImpl` が手書きの `Rc<RefCell<Connection>>` 共有ハンドルだったのをオーナー指摘で是正
**機械強制**: `cargo lint` ルール化予定（候補は下記「機械化の候補」）

## 原則

**シグニチャから内部の振る舞いが予想できるのが良い設計である。** 特別な理由なくそれを隠蔽してはならない。

可変操作は `&mut self` で設計する（第1選択）。`&self` メソッドの裏に `RefCell` / `Cell` /
`Rc<RefCell<_>>` / ロック型を置いて可変性を隠すのは **「`&self` への偽装」** であり禁止する。
偽装すると Rust の借用システムが与える排他性の保証を失い、型を読んでも何が起きるか分からなくなる。

**`&self` + 内部可変性を採るには強い理由が要る**（オーナー明言 2026-08-23）。理由が弱いまま
これを許すと、借用チェッカが働かないコードが積み上がり、**Rust らしいコードでなくなる**。
借用チェッカを効かせることは様式の問題ではなく、この言語で設計の意図を型に載せる唯一の手段
である。したがって本ルールは「例外の一覧」ではなく **立証責任の配置** である — 既定は禁止で、
採る側が理由を示す。

## 判定フロー

```
1. この型は共有される必要があるか？
   ├─ No → &mut self で設計（第1選択。ここで終わり）
   └─ Yes → 次へ

2. 状態変更メソッドが必要か？
   ├─ No → 不変のまま共有（Rc / Arc で十分）
   └─ Yes → *Shared ラッパーを新設（第2選択）
```

### `*Shared`（SharedLock）ラッパーパターン — 内部可変性の唯一の許容ケース

**並行してロックを取りたいなら、手書きではなくこのパターンを使う**（オーナー明言 2026-08-23）。

`&mut self` メソッドを持つロジック型 A が**複数箇所から共有される場合のみ**許容する。

- ロジック本体 A は `&mut self` のまま**残す**（削除しない）。ビジネスロジックはこちらにある。
- 内部可変性は共有ラッパー `AShared` の中**だけ**に閉じる。
- ラッパーは `SharedLock<A>`（書き込み主体、または読み書きが拮抗）または
  `SharedRwLock<A>`（読み込み主体 — 書き込みが稀で参照が多い）を内側に持つ。
  **迷ったら `SharedLock<A>`** を選ぶ。`SharedRwLock<A>` への切替は、実測でホットパスが
  読み込み主体だと判明した時点で行う（推測で選ばない）。
- API は `with_read` / `with_write` のクロージャ形に絞り、**ガードやロックを外へ返さない**。
  ロック区間はクロージャの中に閉じる。

```rust
// ロジック本体: &mut self のまま。ここに借用チェッカが効く
pub struct Xyz { /* state */ }

impl Xyz {
    pub fn do_something(&mut self, arg: T) -> Result<(), XyzError> { /* ... */ }
    pub fn snapshot(&self) -> Snapshot { /* read-only */ }
}

// 共有ラッパー: 内部可変性はここだけ
#[derive(Clone)]
pub struct XyzShared {
    inner: SharedLock<Xyz>,       // 書き込み主体
    // inner: SharedRwLock<Xyz>,  // 読み込み主体
}
```

#### 本プロジェクトでの前提

本リポジトリには現時点で `SharedLock<T>` / `SharedRwLock<T>` に相当する型が**まだ無い**
（参考元の fraktor-rs は `utils-core::core::sync` が提供している）。**共有が必要になったら、
その実装を作ること**（オーナー明言 2026-08-23）— 無いことを理由に `Rc<RefCell<T>>` /
`Arc<Mutex<T>>` の手書きへ逃げてはならない。

導入の作法:

- **共有モジュールに 1 度だけ起こす**（`modules/shared/` 配下）。各 Unit・各所で手書きしない。
- 2 つ目の利用者が現れたときに既存の型を使う。同じ役割の型を並立させない。
- `SharedAccess` 相当の trait を切り、`with_read` / `with_write` だけを公開面に出す。
  内部のロック実装（`std::sync::Mutex` / `RwLock` など）は差し替え可能な内部詳細として隠す。
- 型と同時に**テストを書く**（本プロジェクトは TDD、カバレッジ 90% 床）。

**投機的に作らない。** 共有の必要が実際に生じた時点で作る — 「将来使うかもしれない」で先に
置くのは、下記禁止パターンの「共有が不要な型を `*Shared` でラップする」と同じ誤りであり、
使われない型は死んだコードになる。

現状の U3 は単一所有・単一接続であり、このパターンを要しない（`&mut self` で足りる）。

## 例外 — 強い理由がある場合に限る

例外は自動的に認められる区分ではない。**採る側が強い理由を示し、オーナーの許可を得て、
その理由をコード上のコメントに残す**。理由が「便利だから」「借用が面倒だから」「`&mut` を
呼び出し側まで波及させたくないから」であれば、それは強い理由ではない — 設計をやり直す。

**現在オーナーが認めている型の例外は 1 つだけである。**

### ロックを取り合うメソッド（オーナー明言 2026-08-23）

複数の呼び手が**同時に**呼ぶことを前提とし、内部でロックを獲得して直列化する設計は、
`&self` であることがその意味論を正しく表す（`&mut self` にすると呼び手が排他所有を
持つかのように読めて、かえって嘘になる）。

この例外が成立する条件は次のすべてである。

- その型が**実際に共有される**（複数の所有者・複数の呼び手が同時に存在する）
- 同期プリミティブを持ち、競合を直列化することがその型の責務である
- ロック区間がクロージャ内に閉じ、ガードを外へ返さない
- なぜ `&mut self` では表現できないかが doc コメントに書かれている

単一所有の型の可変操作を `&self` に見せるための逃げ道ではない。共有が「将来ありうる」
程度の見込みも理由にならない — 実際に共有が必要になった時点で `*Shared` を起こす。

## 禁止パターン

- 可変操作のシグニチャを `&self` にし、`RefCell` / `Cell` / ロックで可変性を隠す
- 既存の `&mut self` メソッド（trait メソッドを含む）を `&self` + 内部可変性へ変更する
  — **変更する場合はオーナーの許可が必須**
- `Rc<RefCell<T>>` / `Arc<Mutex<T>>` / `Arc<RwLock<T>>` のような**手書きラッパーの新規作成**
  （共有が必要なら `SharedLock<T>` / `SharedRwLock<T>` を持つ `*Shared` 型として起こす）
- 共有が不要な型を `*Shared` でラップする
- `*Shared` 適用時に元のロジック型を削除する
- ガードやロックを外部へ返す（ロック区間はクロージャ内に閉じる）
- `Clone` が「同じ可変状態を指す別ハンドル」を配る型を作る
  （`&mut self` の排他性が嘘になる。共有が要るなら `*Shared`）

## 命名

| 種別 | サフィックス |
| --- | --- |
| 薄い同期ラッパー | `*Shared` |
| ライフサイクル / 管理責務 | `*Handle` |
| 所有権が一意・同期不要 | サフィックスなし |

## 機械化の候補

優先順は 型（E1）→ 既存 lint → `cargo lint` カスタムルール（README の方針）。

1. `pub fn` / trait メソッドの本体で、レシーバが `&self` かつ `RefCell::borrow_mut` /
   `Cell::set` / `Cell::replace` を呼ぶものを検出する（例外は `// amadeus-lint: allow(<rule>) <理由>` — 抑制構文はリポジトリ共通のこれ 1 つ）。
2. 構造体フィールドに `Rc<RefCell<_>>` / `Arc<Mutex<_>>` / `Arc<RwLock<_>>` が直接現れるものを検出し、
   `*Shared` 型の定義内であることを条件に許可する。
3. どちらも赤例テストを添える（README の DoD）。

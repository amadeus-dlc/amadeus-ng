# フィールドはデフォルト private — 公開はアクセサ経由

**裁定日**: 2026-08-22（オーナー、共通ルール）
**適用例**: フィールド可視性スイープ PR（`UnknownPhase(pub String)` 型の全面見直し）
**機械強制**: `cargo lint`（`no-public-fields` — 無制限 `pub` フィールドをフィールドごとに検出。`pub(crate)` 等の restricted visibility は非検出）

## ルール

- **構造体のフィールドはデフォルト private**。`pub struct X(pub String)` / `pub struct X { pub field }` のように内部構造をさらけ出さない。エラー型・値レコード・newtype も例外ではない。
- 読み取りは**アクセサメソッド**で公開する。ただし**アクセサを置く前に**
  [tell-dont-ask.md](tell-dont-ask.md) §追記 の 3 段階を通すこと — ①そもそも出さずに済まないか
  （判断を型へ移す）②ドメインの意味を持つクエリにできないか ③境界を越える変換なら変換として
  名乗る。**「フィールドを private にしたから機械的にアクセサを生やす」は本ルールの意図ではない**
  （下記 §根拠 の「アクセサの存在は I/O 境界のためにある」と同じ趣旨。土台
  [abstract-data-type.md](abstract-data-type.md) の「暴露と変換の違いは名前ではなく必要性にある」）。
  ③に落ちる境界変換アクセサには、**なぜ境界なのかを doc コメントに一行**書く
  （他規則の例外作法と揃える）。命名は既存の house style に従う:
  - `String` フィールド → `pub fn as_str(&self) -> &str`（単一 String newtype）/ `pub fn message(&self) -> &str`（メッセージ担体）/ フィールド名そのまま（`pub fn scope(&self) -> &str` 等。`get_` 接頭辞は付けない）
  - `Vec<T>` → `&[T]`、`Copy` 型 → 値返し、その他 → `&T`
- 定義モジュール外から構築が必要な型（Gateway が組み立てる値レコード・テストが構築するエラー値）には `pub fn new(..)` を与える。不変条件を持つ型は従来どおり private ctor + `parse`（Always Valid）。
- **enum の変種フィールドは言語仕様上 private にできない**ため本ルールの対象外（変種フィールドの公開が問題になる型は struct への昇格を検討する）。
- ~~`pub(crate)` は同一クレート内の実装詳細共有にのみ許す（既定はやはり private）。~~
  → **失効（2026-08-24 オーナー裁定）**。`pub(crate)` も禁止で例外を認めない。
  詳細は下記 §改訂 2026-08-24。カプセル化の単位はクレートではなく `struct` である
  （[abstract-data-type.md](abstract-data-type.md)）。

## 根拠

内部構造の直接公開は表現の変更（フィールド追加・型変更・不変条件導入）を破壊的変更にし、Tell-Don't-Ask 違反（[tell-dont-ask.md](tell-dont-ask.md)）の入口になる。アクセサ経由なら表現を変えても契約面が保たれる。

アクセサの**存在**は I/O 境界（リポジトリ・Gateway・シリアライザ・Presenter）のためにある — private フィールド + アクセサは境界での利用を妨げない。禁じられるのはビジネスロジック領域でアクセサから所有者の判断を再実装すること（tell-dont-ask.md の適用領域を参照）。

## 改訂 2026-08-24（オーナー裁定）— `pub(crate)` も禁止、例外は認めない

> **土台**: [abstract-data-type.md](abstract-data-type.md) §「カプセル化の単位は `struct` で
> あって `mod` ではない」。`pub(crate)` は「カプセル化の単位をクレートと取った」という告白で
> あり、クレートは単位ではない。「同一クレート内の実装詳細だから」は**悪魔のささやき**
> — それを認めるなら private の存在意義が消える。

**`pub` も `pub(crate)` も、理由なしに使ってはいけない。そして本ルールに例外は認めない**
（オーナー明言 2026-08-24「pub or pub(crate) フィールドは理由なしに使ってはいけない」
「これに関しては例外認めなくてもいいかも」）。

従来 `cargo lint` の `no-public-fields` は**無制限の `pub` だけ**を検出し、`pub(crate)` /
`pub(super)` は「同一クレート内の実装詳細共有にのみ許す」として見逃していた。その条件付き
許可が実際には骨抜きに使われる — 実測（2026-08-24）: `WorkflowExecutionState` は
**アクセサを 17 本持ちながら**フィールド 16 本を `pub(crate)` にし、同一クレート内から
**52 箇所**が直接触っていた。入口が二重で、フィールドを 1 つ変えると 52 箇所が壊れる。
高凝集・低結合の妨げであり、リファクタリングの足かせになる。

### 射程（対象外）— 2026-08-24 追加

「例外を認めない」は**射程の中で**の話である。次は**そもそも本ルールの対象外**であり、
例外ではない（[abstract-data-type.md](abstract-data-type.md) §対象外 と同じ範囲）。

- **ワイヤ表現・外部形式の DTO**（`interface-adapter/src/orchestration/wire/` など、
  serde の外部表現を写す型）— ドメインの抽象データ型ではなく、外部形式の写しである
- **infrastructure の汎用モジュール**（`core-infrastructure::canon_json` など）— ドメインを持たない部品（2026-08-29 の shared 解体で移設）
- **`enum` の変種フィールド** — 言語仕様上 private にできない

この 3 つの外に例外は無い。

### 検出境界の拡張

`cargo lint` の `no-public-fields` を `pub(crate)` / `pub(super)` / `pub(in path)` まで
広げる。**射程の中に例外は無い**が、上の対象外は検出しても抑制コメントで通せる形にする
（実装の現状もそうなっている — `check.rs` の `is_suppressed` は理由付き allow を一律に
受け付け、緑テスト `r3_is_suppressed_by_a_matching_allow_comment` が「serde の外部表現
(境界の DTO)」という理由での抑制を固定している）。

**したがって作法は「抑制不可」ではなく「抑制には理由が必須、かつ理由は上の 3 つの
いずれかであること」**である（2026-08-24 の初稿は「抑制コメントは受け付けない」と書いたが、
実装と既存テストに反していた — 規則整合監査 M6）。

### 同一モジュール内の構造体リテラルはどうするか

集約が自分のスナップショット型を組み立てる／分解するようなコードは、フィールドが private でも
**同一モジュール内なら書ける**。跨ぐ必要があるなら、それは**完全コンストラクタが無い合図**で
あって可視性を緩める理由にはならない（[factory-naming.md](factory-naming.md)「コンストラクタ
相当は `fn new(..) -> Self`」/ オーナー原則「完全コンストラクタがあれば `set_xxx` は不要」）。

### 導入の順序

検出を広げると既存の違反で `cargo lint` が赤になる。**リンターの拡張と既存違反の是正は
同じ Bolt で同時に着地させる**（例外を認めない以上、一時的な allow を置いて先行させることは
できない）。

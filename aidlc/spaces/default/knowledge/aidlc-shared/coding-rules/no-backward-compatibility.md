# 後方互換のコードを残さない — 改名・変更は一斉に、呼出側ごと直す

**裁定日**: 2026-08-23（オーナー）
**適用例**: U3（Bolt B5）— `SqliteEventStore` → `EventStoreImpl` の改名、`store(&self)` → `&mut self` のレシーバ変更を、いずれも旧名の別名や旧署名の互換口を残さず一斉に実施
**機械強制**: `cargo lint` ルール化候補（`#[deprecated]` の検出）。現状はレビュー基準

## ルール

型・メソッド・モジュールの名前や署名を変えるときは、**旧いものを残さない**。

- `#[deprecated]` を付けて旧 API を残さない
- 旧名の型エイリアス（`pub type SqliteEventStore = EventStoreImpl<..>;`）を置かない
- `pub use new_name as old_name;` の別名再エクスポートをしない
- 旧署名を新実装へ委譲する薄い互換メソッドを並立させない
- 「移行期間」を理由に 2 つの口を同時に生かさない

**呼出側ごと一斉に直す。** コンパイラが全ての呼出箇所を挙げてくれるので、それが移行の作業リストである。

## 根拠

本リポジトリは**まだ公開配布していない**（`cargo install` 配布は計画段階、ADR 0005 A1）。
外部の利用者が存在しないため、互換のために払うコストの対価が無い。一方で互換口を残すと:

- 同じ役割の口が 2 つある状態が固定化し、どちらが正なのか読んで分からなくなる
- 旧口を使う新規コードが生まれ、移行が終わらない
- テストとカバレッジが二重になり、実質使われない経路が床を押し上げる
- 「シグニチャから内部の振る舞いが予想できる」という設計の前提
  （[interior-mutability.md](interior-mutability.md)）が、口の重複で崩れる

## 対象外

- **upstream 互換**は別問題である。`docs/specs/` が定める upstream（AI-DLC ワークフロー本体）との
  観測可能な契約は維持する。本ルールが禁じるのは**自分のコードの中の**互換口であって、
  upstream が観測する振る舞いの互換ではない。
- 監査証跡・履歴記述（過去のレビュー所見、`pending-revision.md`、`deviations.md` の記録）は
  コードではない。消さずに残し、失効した旨を追記する。
- **公開配布を開始した後は本ルールを見直す。** 外部利用者が現れた時点で、
  semver と非推奨期間の方針をオーナー裁定で定める。

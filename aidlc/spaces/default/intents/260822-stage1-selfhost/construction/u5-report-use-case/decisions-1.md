# B11 設計裁定と申し送り（2026-08-29 セッション）

本 Bolt（U5 = report ユースケース、FR2.1 のみ）に先立ってオーナーが下した裁定と、
その過程で見つかった未処理事項の記録。裁定はブリーフ `brief-1.md` の「固定裁定」に
反映済みで、本ファイルは**根拠と経緯**を残すためのもの。

## 確定した裁定

### 裁定 1 — 投影キャッチアップの起動は合成ルート（U7）

**問題**: 上流成果物どうしが矛盾していた。

- `unit-of-work.md` の U5 責務: 「… → store → **投影キャッチアップ起動**」
- `unit-of-work-dependency.md`: `U5 → U4` の依存辺（理由「コマンド末尾の投影キャッチアップ起動」）
- 一方 `coding-rules/cqrs-boundaries.md`（2026-08-29 オーナー裁定・**クレート分離で機械強制**）:
  「コマンド側・クエリ側が RMU を `Cargo.toml` に書く」は禁止パターン、「合成ルート（U7）は
  RMU を**起動するだけ**」
- `unit-of-work.md` の U7 責務にも「コマンド末尾の ReadModelUpdater 起動」が重複記載

**裁定**: 起動するのは **CLI の起動部分（合成ルート U7）**。U5 は RMU に依存しない。

**根拠の補足**: 本プロジェクトは常駐プロセスを持たず、`aidlc report ...` は 1 回走って終わる
CLI である。AWS 版なら DynamoDB Streams が RMU を非同期に叩くが、SQLite にストリームは
無いので、同一プロセス内で誰かが `catch_up()` を明示的に呼ばないと最新化が起きない
（`cqrs-boundaries.md`「SQLite にはストリームが無いので、AWS 版 RMU が Streams から
受信するのと同じ役割を、ここでは自分で引く形で果たす」）。その「引く」きっかけを誰が出すか、
が論点だった。**RMU が最新化を行うこと自体は論点ではない。**

**反映**: `unit-of-work.md` の U5 責務文と `unit-of-work-dependency.md` の
mermaid 辺・text fallback・辺の根拠表を、いずれも失効注記付きで in-place 修正済み。

### 裁定 2 — フェーズ境界は集約が内部導出する

**問題**: `workflow_execution.rs:532` は「`phase_boundary` は**呼出側が導出**して渡す投影材料
（C5）」として `approve_gate` の引数にしている。一方オーナー統一ルール（project.md
Corrections 2026-08-22）は「集約は FSM。判断（クエリメソッド）を集約型に閉じ込め、
ユースケースは進行管理・フロー制御のみ（**ビジネスロジック禁止**）」。
「この承認がフェーズ境界をまたぐか」は集約状態からの判断であり、現状のままだと U5 に
ビジネスロジックが入る。

**裁定**: **集約が自分で導出する**。`approve_gate` の `phase_boundary` 引数を廃止。

**オーナー補足（重要）**: これは**本家仕様からの逸脱ではなく、内部の実装方法の選択**である。
したがって外形は 1 バイトも変えない — `GateApproved` の payload 形（`phase_boundary` を持つ）、
監査シャードのバイト列、`aidlc-state.md` の差分はすべて現状どおり。ゴールデン
（`cli/report/approved-across-phases` 等）と RMU の投影ゴールデンテストで機械的に固定する。

### 裁定 3 — `StoreVersion` newtype 化は却下

**問題**: B7 の申し送りに「楽観 version の newtype 化は U5/U6 の境界強化候補」とあった
（`workflow_execution_repository.rs` の trait doc）。

**裁定**: **却下**。楽観ロックの判定そのものは本家 `event-store-adapter-rs` v3.0.0 が行っており
（`EventStore::persist_event_and_snapshot(..., expected_version: usize)`、失敗時は
`optimistic lock failed, aid=..., expected_version=...`）、`usize` はその本家が定めた語彙である。
こちら側で専用型の衣を着せるのは Conformist 方針（`=3.0.0` ピン・腐敗防止層なし、
`coding-rules/upstream-contracts.md`）に反する。`usize` のままポートを往復させる。

**残るリスク**: `version` と `seq_nr` がどちらも `usize` なので型では取り違えを止められない。
緩和はポート doc の 3 か条（ストア採番のトークン・`seq_nr` と混同しない・集約へ入れない）と
テストに委ねる。

## 追補（実装着手後に判明した事項・2026-08-29）

### 訂正 — ブリーフ初版の `Conflict` 再試行の記述は誤りだった

初版ブリーフは固定裁定として「再試行の政策は持たない（`Conflict` も再試行しない — ポート doc
C3 ③）」と書いていた。これは**メインセッションによる C3 ③ の誤読**であり、委任先の指摘を受けて
正本を確認して撤回した。

正本は `inception/contract-design/contract-design-questions.md` の **Q6 = A**（オーナーが
`[Answer]: Looks correct` で承認済み）:

> 楽観 version 競合は即 `Err`（**ユースケースが 1 回だけ再水和して再試行**、それでも競合なら
> CLI がエラー終了。ワンショット CLI で同時実行は稀）

C3 ③「`Conflict` **以外**のエラーはリトライしない」は「Conflict **だけ**が再試行の対象であり、
その政策はユースケースが持つ」の意である。したがって:

- `repository_error.rs` の `Conflict` doc（「ユースケースは再水和して 1 回だけ再試行する」）は
  **正しい**。変更しない。
- `ReportUseCase` は `store` の `Conflict` に対し、**再構成（`find_by_id`）からやり直して**
  1 回だけ再実行する。2 回目も `Conflict` なら伝播。再試行後に集約コマンドが `Err`（別クローンが
  先に承認しゲートが閉じた等）を返す場合も伝播。

**教訓**: 委任ブリーフに固定裁定として書く前に、根拠として引く 1 次資料（ここでは C3 の条項）を
**当たり直すこと**。要約（trait doc の 1 行）を根拠に裁定を書くと、要約の圧縮で意味が反転しうる。

### 所有ファイル規律の例外承認

裁定 2 で `approve_gate` の引数が 1 つ減るため、所有ツリー外の呼出側がコンパイル不能になる
（`no-backward-compatibility.md` により互換オーバーロードは残さない）。`approve_gate` の呼出は
**全 7 箇所**（委任先の初報は 5 箇所で、所有ツリー内の domain tests 2 箇所が漏れていた）。
すべてリテラル `None` を渡しているだけなので、**`None,` の削除に限り**所有ツリー外 5 箇所の
編集を承認した。詳細は `brief-1.md` の「所有ファイル・規律」を参照。

### C3 ④ とコーディング規則の緊張（記録のみ・是正不要）

契約 C3 ④（2026-08-27 / ADR-010 改訂）は「テストダブル型は無く、テストは
`XxxUseCase<WorkflowExecutionRepositoryImpl<…>>` で組む」と定めるが、これを use-case クレート内の
テストで literal に満たすには `core-command-interface-adapter` を dev-dependency に足す必要があり、
`use-case-rules.md` §1 の機械強制（「`core-use-case` の `Cargo.toml` に `core-interface-adapter` が
無いこと」）が壊れる。加えて依存が循環する。

**採った解**: 網羅テストは use-case クレート内のスクリプト可能な fake で持ち（`Conflict` を意図的に
起こすにはどのみち fake が要る）、C3 ④ は `interface-adapter/tests/` に結線テスト 1 本を置いて
満たす。両方の要求が同時に満たされるため、C3 ④ の改訂は不要と判断した。

### 裁定 6（2026-08-29・後刻）— `CorruptCause` をポート契約から退避する【申し送り (b) の上書き】

> **実装済み 2026-08-30（Bolt B13）** — `RepositoryError<Id>` ジェネリック化と同時に適用。`corrupt_cause.rs` は削除、原因はアダプタ私有 `CorruptDetail` を `source` 連鎖で運ぶ。

先の「(b) 一旦許容」を**オーナーが後刻上書き**した。論点も「置き場所」から「**エラーは契約の
一部であり、契約に内部実装がバレる情報を含めるべきでない**」へ深まった。

**確定した事実**（実測）:

- `CorruptCause` の 4 分類のうち `UndecodablePayload`（直列化の都合）と `MissingSnapshot`
  （格納方式の都合）は実装語彙であり、ポート契約（ユースケース層所有）に漏れている。
- この分類で分岐する消費者はゼロ。契約として約束する必要が無い情報が実装を縛っている。
- `error-handling.md` は「`String` の文言を運ぶ変種を作らない」を定めるため、
  説明文字列へ落とす逃げ方は使えない。

**裁定**: `RepositoryError::Corrupt` を `{ aggregate_id, seq_nr, source }` とし、`source` は
標準ライブラリの原因連鎖（`Error::source` — 中身の型を約束せず診断表示だけを運ぶ標準手段）で
**アダプタ自身の内部エラー型**を載せる。契約は「壊れていた」としか約束しない。分類
（MissingSnapshot 等）は**アダプタの私有物**へ移り、CLI の診断表示（caused by: ...）は残る。
use-case 層の `corrupt_cause.rs` は**削除**。

**代償として受容**: `Corrupt` 変種は等値比較できなくなる（`PartialEq` から外れるか手実装で
除外）。既存アダプタテストの `assert_eq!` は `matches!` + source の文字列確認等へ書き換える。

**RMU の同名型は対象外**: RMU の `CorruptCause` は `JournalReadError` の材料で、ポートも実装も
RMU クレート内にあり（読む側と読まれる側が同一クレート）、クレート境界を越えて漏れる契約では
ない。今回は触らない。

**実施タイミング**: B11 と衝突するため（`repository_error.rs` は B11 の委任先所有ツリー、
アダプタ実装・テストはその外）、**B11 着地後の小さな追随 PR** として実施する（PR 直列運用）。
B11 委任先には「新規コードで `CorruptCause` への結合を増やさない」ことだけ通知した。

### 裁定 7（2026-08-29・後刻）— 改名 CommitVerdictUseCase と CQS 適合形への再設計

**経緯**: `ReportUseCase` という名前がオーナーに「レポート（帳票）を作る／読むユースケース」と
誤読された。ここでの report は upstream CLI の動詞（コンダクタがステージの結末を報告する =
遷移コミット）であり帳票ではないが、**プロジェクトを最も知る読者すら誤読させた時点で名前の
失格**。名前の出どころは `use-case-rules.md` の適用例（CLI 動詞＝ユースケース）で、この命名
規約自体が動詞衝突（report 報告 vs レポート）を見落としていた。

さらに CQS 例外（`execute(&mut self) -> Result<ReportOutcome, _>`）の許可要請に対し、オーナーが
「イベントを基に RMU で作ったリードモデルを読めばよい。これを許せば他でも許すことになる」と
却下。検討の結果、**却下が正しい**:

- この CLI では RMU の catch_up が同一プロセス内で同期実行されるため、コミット直後に U7 が
  catch_up を呼べばリードモデルは最新であり、Presenter の材料はそこから読める（読むのは
  合成ルート = 「両側を知ってよい」側）。
- 「別トランザクションで食い違う」という当初の擁護は、Q6 が既に「稀」と裁定済みの同一クローン
  同時実行の話で、戻り値でも同じ競合は起きるため理由にならない。
- **集約コマンドがイベントを返すのとは別物**: あれは `store()` へ渡す書込パイプラインの配管
  （B3 レビュー通過済みの家風）。ユースケースの Outcome 返しは Presenter に読ませる読取
  チャネルであり、CQRS の迂回。この線引きを precedent として記録する。

**裁定**:

1. 改名: `CommitVerdictUseCase`（報告された結末 Verdict をコミットする — 更新意図が先頭）。
   エラーは `CommitError`。`use-case-rules.md` 適用例の `ReportUseCase` 表記も更新する
   （coding-rules の編集はメインセッションが行う — 委任先は禁止ツリーのまま）。
2. `execute(...) -> Result<(), CommitError>` — 規則が許す Command の形（`Result<(), E>`）。
   `ReportOutcome` は削除。何もコミットしない成功（ゲート既開・BR1.9 通過済み）も `Ok(())`。
   「何が起きたか」は U7 が catch_up 後のリードモデル（状態ファイル・監査シャード末尾）から
   導出する — その Presenter 設計は U7（FR4）の課題として申し送る。
3. `Resumed` を入力型から削除。resume のルーティングは Controller（U7）が手前で分岐する —
   `use-case-rules.md` §3 が既にそう定めており、ユースケース入力に入れた B11 当初の形は
   規則に反していた。FR2.1 の「resumed」はこの U7 側ルーティングで満たす（upstream の
   `handleResumeReport` も同じ構造）。

**教訓**（メインセッションの反省）: CQS 例外を 2 度「許可推奨」で提示し、2 度とも誤りだった。
同期 catch_up の存在を見落として「リードモデルから読めない」と誤断し、配管（集約のイベント
返し）と読取チャネル（Outcome 返し）を「同じ家風」と混同した。例外を推す前に、規則が守れる
設計が本当に無いかをリードモデル側の能力まで含めて検討すること。

### 裁定 7 追補（2026-08-29・オーナー確定）— 読取はクエリユースケース経由

裁定 7 の「何が起きたかは U7 がリードモデルから導出」を、オーナーがより正確な形で確定した:
**CLI サブコマンドの出力データは、コマンドユースケース起動 → RMU 実行（リードモデル作成）→
クエリユースケースがそのリードモデルを読んで返す**、という経路で得る。

- クエリユースケースは `core/query/*` の新設モジュール群（`cqrs-boundaries.md` が既に予約
  している「将来のリードモデル読取・クエリ API 層」の実体）。
- 境界: クエリ側は**ドメイン（`core-command-domain`）に絶対依存しない**（既裁定）。返すのは
  クエリ側が所有する読取用の型であり、コマンド側のイベント・集約は現れない。
- 文言は従来どおり出す側（U7 Presenter）が組む。クエリユースケースはデータを返すだけ。
- 実施時期: U7（FR4）の Bolt で最小のクエリユースケースを新設する（それまでコマンド側の
  再設計 = B11 再作業はこの申し送りだけで完結する）。

### 裁定 7 追補の訂正（2026-08-29・オーナー指摘）— リードモデルは .md に限らない

直前の追補は、クエリユースケースの読み先を暗黙に既存の .md ファイル群（`aidlc-state.md`・
監査シャード）に縛っていた。それではクエリユースケースが upstream 互換 Markdown を逆パース
することになる。オーナー指摘により以下へ訂正する:

- **リードモデルは消費者ごとに複数あってよい。** `aidlc-state.md`・監査シャードは
  「upstream 互換・人間可読・git 交換用」のリードモデル（バイト逐語が契約）。**クエリ
  ユースケースに仕えるリードモデルは別に、SQLite 上のテーブルとして** RMU が同じイベント列
  から投影してよい。
- **既存設計が既に複数投影を予約している**: チェックポイント表は `projection TEXT PRIMARY
  KEY`（投影名がキー）で投影ごとに独立前進でき、`ProjectionName` 型も既にある。現行
  `ReadModelUpdater` は単一投影を駆動する形なので、複数投影の駆動（updater の複数インスタンス
  か多対象化）は U7（FR4）時点の設計課題。
- クエリ側はそのテーブルを自前のアダプタで読む（rusqlite は外部ライブラリで側判定の対象外。
  コマンド側クレートへの依存は生じない）。返すのはクエリ側所有の読取型。Markdown パースは
  設計から消える。
- テーブルの具体設計（何を列に持つか）は U7 の Bolt で、Presenter が必要とする材料
  （直近コミットの動詞・ステージ・スコープ等）から逆算して決める。

### 裁定 7 追補 2（2026-08-29・オーナー確定）— コマンドサイドとリードモデルは別データ

- **コマンドサイドは完全に正規化されている**: `journal`（1 行 = 1 イベント、追記のみ、導出
  データなし）と `snapshot`（集約状態 + 楽観 version）。ここだけが正本であり、提示のために
  読むことはない。
- **クエリサイドのリードモデルは非正規形式が普通**（正規化されていてもよいが、**要件が違う
  ので別データ**）。既存の `aidlc-state.md`・監査シャードは「人間・git 交換」要件の非正規化
  （描画済みテキスト）。U7 のクエリ向きテーブルは Presenter の問いに読み時結合なしで即答
  できる形から逆算する。ジャーナルのスキーマをなぞる義務はない。
- 別データであることの含意: リードモデルは導出物であり**捨てて再生成できる**ことが設計条件
  （C5「再生成は空の投影先から全イベントを再適用」が既に規定）。

### 裁定 7 追補 3（2026-08-29・オーナー要件）— RMU の投影は非同期に動く

オーナー要件「RMU のプロジェクションは非同期に動いててほしい」。U7（FR4）の設計条件として
記録する:

- 各投影は **spawn された非同期タスク**として走る。コミットは投影の完了と無関係に成立し、
  投影の失敗・遅延はコマンドをロールバックしない（Q6 = A の既裁定と同義）。
- **合流点は 2 つ**（要件が違うので別々に待つ）:
  1. upstream 互換の .md・監査シャード投影 — **プロセス終了前に join**。ゴールデンが
     「コマンド終了後のバイト」を比較する以上、ここだけは待つことが U1 検収の前提。
  2. クエリ向きテーブル投影 — **クエリユースケースが読む直前に U7 が join**（需要駆動の
     read-your-own-writes。読まないコマンドでは待たない）。
- 投影同士は並行に走れる（チェックポイント表の projection キーによる独立前進が既に前提）。
  tokio current_thread（Q3 = A・Send 境界なし）では spawn_local で成立。
- 待たれなかった窓・クラッシュ窓は次回起動の冪等キャッチアップが修復（既裁定）。
- **未確定**: 常駐プロセス（デーモン）での連続投影まで要件に含むか。含む場合は .md 契約との
  整合を含め別途設計（オーナーへ照会済み・回答待ち）。

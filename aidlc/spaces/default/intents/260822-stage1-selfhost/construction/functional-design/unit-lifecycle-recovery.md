# 複数監査ファイルで完了記録を見落とす問題の修復

## 原因と修正

2026-09-05、U9 の UNIT_COMPLETED が記録されたにもかかわらず、次の指示が同じ U9 に戻る事象を確認した。

作業回の基準を求める関数は、監査行が引数で渡されると整列済みと仮定していた。しかし、読取関数の結果はファイルごとの並びであり、全体の時刻順ではない。そのため、完了を記録する側と完了を読む側で採用する作業回が違っていた。

修正前の実測:

- 記録側: `GATE_REJECTED:2026-09-05T06:37:27Z#1`
- 読取側: `STAGE_JUMPED:2026-08-22T09:31:03Z#4`
- 認識された完了: U1 / U2 / U3。U9 は進行中と判定された。

監査行が引数で渡される場合も、時刻・ファイル・ファイル内位置を整列してから作業回を選ぶよう修正した。同秒の異なる監査ファイル間で因果順序を確定できない場合の AMBIGUOUS 判定は維持した。

修正後は両側とも `GATE_REJECTED:2026-09-05T06:37:27Z#1` を採用し、U9 を完了、進行中項目をなしと判定した。次の指示は U1 に進み、U9 の繰り返しは解消した。既存の監査行は変更していない。

## 配布と検証

`scripts/aidlc-sync/patches/unit-lifecycle-audit-order.patch` に修正を置き、同期スクリプトで .claude / .codex / .kimi-code に同じ修正を適用した。vendor のコミットとバージョンは変更していない。

回帰テストは `scripts/aidlc-unit-lifecycle.test.ts`。各ハーネスについて、入力順によらない最新回の選択、同秒・同一ファイルの位置順、同秒・別ファイルの曖昧性、新しい完了記録の認識と古い完了の失効を確認する。実プロジェクトの状態に依存しない一時ディレクトリで実行する。

- 修正前: 回帰テスト 12 件中 6 件失敗。U9 の代わりに古い Unit を完了とする誤判定を再現。
- 修正後: 回帰 12 件 + 同期 9 件 = **21 件成功、0 件失敗**。
- `bun scripts/aidlc-sync.ts --check`: コピー 0、削除 0、保持設定の確認 0。
- 実プロジェクトの完了記録読取: U9 の完了を認識。

## 残作業の再判定

直前の機能設計の変更要求が現在の作業回を定めるため、古い作業回の U1〜U3 の完了記録を現在の完了として持ち越すことはできない。ただし、その成果物と要約確認は残っており、確認証拠の検査は成功している。

| 対象 | 再判定時点の状態 | 次の扱い |
| --- | --- | --- |
| U9 | 新しいレビューと完了記録あり | 完了として保持。レビュー所見は未解決事項として残す |
| U1 / U2 / U3 | 必須設計 4 ファイルと有効な要約確認あり。完了は古い作業回 | 保存済み設計と現在の契約を再検証する。実装のやり直しとは扱わない |
| U4 / U5 / U6 / U7 / U8 | 正式な Unit パスに機能設計の必須成果物が不足 | 既存実装・後続裁定を確認し、必要な設計記録を補完する |
| U10 | packaging。機能設計の必須成果物は適用外 | 欠落と数えない |

したがって、以前の「残り6件」は誤った作業回を読んだ結果である。機能設計で再確認・補完が必要な対象は U1〜U8 の8件。別名の旧ディレクトリの存在を、正式 Unit の完了証拠に読み替えない。

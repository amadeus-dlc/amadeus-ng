# U3 イベントと集約の取り違え防止

2026-09-05。設計の「別集約のイベントを渡すことは型で防げる」という主張を実際の保存経路で検証した。

## 再現と修正

IntentExecution、WorkflowDefinitionはいずれも、イベントと適用後集約を独立した参照引数として受け取る。同じ型でも異なる集約IDを持つ組を渡せる。

修正前は、別実行のStartedと対象IntentExecution、別系譜のDefinedと対象WorkflowDefinitionの保存が、SQLiteとメモリの両方で成功した。拒否を期待するテストは各2件、合計4件失敗した。期待版や通番が適正でも、封筒の外側IDとpayload内の集約IDが食い違う書込を作れた。

両Repositoryのstore入口に、イベントのaggregate_idと対象集約のidの照合を追加した。不一致なら、ストアを呼ぶ前に既存のRepositoryError::Corruptを返し、私有のWriteContractを原因として保持する。IDが一致する場合の保存処理、楽観版によるCAS、初回スナップショット、設定間隔による更新、差分再生は変更していない。

IntentRepositoryには、Createdから起こした集約と保存対象全体を照合する処理が既にある。処理は追加せず、古い実行イベントの説明だけを訂正した。

## 試験とレビュー

| 対象 | 修正前 | 修正後 |
|---|---|---|
| IntentExecutionの取り違え | memory/SQLiteとも拒否期待が失敗 | 共通契約22件＋実装固有23件、計45件成功 |
| WorkflowDefinitionの取り違え | memory/SQLiteとも拒否期待が失敗 | 共通契約14件＋実装固有12件、計26件成功 |

追加した共通契約は、新規保存の拒否後に両IDがNotFoundのままであることと、更新拒否後も対象の元状態を再読取できることを検査する。既存の正常保存・再構成・楽観競合の試験も同時に実行した。

ログは `/tmp/verify-this/u3-event-pair-{red,green}.log`、`u3-definition-pair-{red,green}.log`。独立の読み取り専用レビューで、実行側のID照合、保存状態の保全、CASへの非干渉を確認した。定義側の最終確認と最新全体検証は別途統合記録に記載する。

## 保証範囲

この検査が保証するのはイベントと保存先の集約IDの一致である。同一IDの任意のイベントと任意の適用後状態が意味的に対応することまで証明しない。呼出側は同じコマンドから得たイベントと適用後集約を渡す。

集約の再構成は、最新スナップショットとその通番より後の差分イベントを使う確定方針を維持する。今回の修正は再生範囲を全ジャーナルへ広げるものではない。
